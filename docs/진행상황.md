## 시스템 개요

### 무엇을 만드는가

**관광지 혼잡 조기경보 시스템.** 콘텐츠 확산을 신호로 삼아 방문 급증을 **사전에** 감지하고, 지자체가 취할 조치를 **매뉴얼 근거와 함께** 제시한다.

기존 혼잡 관리는 현장에 사람이 몰린 뒤에 대응한다. 우리는 그보다 앞선 신호 — 유튜브·검색·소셜 — 에서 출발한다. 거제 사례에서 확인했듯 **콘텐츠 확산과 방문 급증 사이에는 수 주의 시차**가 있고, 그 시차가 곧 대비할 수 있는 시간이다.

### 에이전트 5종

| 에이전트 | 역할 | 산출 JSON | 상태 |
| --- | --- | --- | --- |
| ① 사례 타임라인 | 콘텐츠 확산 → 방문 급증 → 조치 → 완화의 전개를 시간축에 재구성 | `timeline.json` | 다음 주 |
| ② **콘텐츠 유형 분류** | 영상이 만들어내는 수요의 성격을 판정 | `content_type.json` | **실행 완료** |
| ③ 매뉴얼 매칭 | 현재 상황에 해당하는 매뉴얼 조치를 골라옴 | `checklist.json` | **실행 완료** (판정은 세션 내, API 연결 후 재실행) |
| ④ 선례 조사 | 데이터랩이 추천한 유사 지역이 과거 어떻게 대응했는지 뉴스·보도자료에서 찾아 요약 | `precedent.json` | 다음 주 |
| ⑤ 브리핑 생성 | 위 결과를 담당 공무원이 읽는 문장으로 종합 | `briefing.json` | **실행 완료** (판정은 세션 내, API 연결 후 재실행) |

에이전트 ①④는 이번 주에 구현하지 않는다. 사전 생성된 JSON으로 시연이 가능하기 때문이다.

### 화면 5개 (AREA)

| 화면 | 내용 | 주로 읽는 JSON |
| --- | --- | --- |
| **AREA 0** 관제 대시보드 | 현재 경보 단계와 근거를 한 화면에. 시연 첫 화면이자 대표 스크린샷 | `signal_status` `forecast` |
| **AREA 1** 신호 스캔 | 누가 오고 있고 어디로 몰리는가 | `visitor_profile` `hotspots` `forecast` |
| **AREA 2** 콘텐츠·유형 (4탭) | 어떤 콘텐츠가 수요를 만들고 있는가 | `content_type` |
| **AREA 3** 정책 브리핑 | 그래서 무엇을 해야 하는가 (매뉴얼 근거 포함) | `checklist` `precedent` |
| **AREA 4** 성과 리포트 | 조치가 효과가 있었는가 | `before_after` `timeline` |

*화면-JSON 매핑은 역할3과 최종 확정이 필요하다. 스키마는 이미 고정되어 있으므로 어느 화면에서 읽든 구조는 동일하다.*

### 이 프로젝트가 지키는 원칙

1. **출처 없는 값은 화면에 올라가지 않는다** — 주장이 아니라 스키마로 강제한다(`source`·`period`·`caveat` required)
2. **AI가 정책을 창작하지 않는다** — 모든 조치는 매뉴얼 원문과 쪽수를 달고 나온다
3. **거른 것도 보여준다** — 제외 건수를 숨기지 않는다
4. **거제 하나를 끝까지** — 다른 지역은 거제가 완성된 뒤 복제한다

### 이 대회는 "성과 창출 사례" 공모전이다 — 팀은 이미 대응하고 있다

서식4의 예시는 전부 **이미 실행해서 낸 성과**다 — "방문객 수 200% 증가", "연안사고 18.5% 감소". 작년 대상작(강진군)도 방문자 43만 명 증가·소비 69억 원이라는 실측 숫자로 받았다.

지난 회의에서 **SurgeLens(분석·백테스트)를 뼈대로, 노칫 얼럿(서비스)을 흡수**하기로 한 결정이 정확히 이 문제에 대한 답이다. 백테스트는 **사용자가 0명이어도 숫자가 나온다.** 서술 비중도 본론 70%(lead-lag 규명) : 제언 30%(서비스)로 정해져 있다.

**따라서 계량성과의 축은 백테스트다**
- 리드타임 — 콘텐츠 확산 대비 며칠 먼저 탐지 가능했는가
- 적중률 — 과거 급증 구간 중 몇 건을 사전 탐지했는가
- 거제 읍면동 방문 집중도(지니계수, 매뉴얼 Tier1 KPI) — 콘텐츠 확산 전후의 쏠림을 공사 지표로 증명
- ~~거제 조치(6.12) 전후 비교~~ → 6.12는 가격 대책이라 혼잡 효과 주장은 약하다. 회의에서 결정
- 제시 조치 중 매뉴얼 출처 명시 비율 (100%) — 성과가 아니라 **신뢰성** 서술에 쓴다

정리본: **`docs/계량성과_후보.md`**

**미확정**: 서식4의 성과분야 6개 중 1개를 선택해야 한다. 본론이 분석인 점을 감안하면 「전략수립 및 기획」 또는 「관광지 안전문제 해결」이 후보이고, 서비스 산출물을 앞세우면 「앱·웹 등 서비스 개발」이다. **회의에서 확정 필요.**

### 서면심사는 서식4 3장이 전부다

- 서식4 분량: **최소 2장 ~ 최대 3장**, 함초롱바탕 11pt, 줄간격 160, 개조식
- 웹서비스는 '응모작 관련 참고자료(**선택**)'로 Zip 첨부
- 1차 통과(상위 9위) 후 **발표심사 8분 PT + 7분 질의응답**에서 웹 시연이 위력을 발휘한다

**순서를 헷갈리면 안 된다.** 웹을 아무리 잘 만들어도 서식4 3장이 약하면 발표까지 못 간다. 반대로 서면을 통과하면 웹 시연이 결정적이다.

### 공모요강이 우리 매뉴얼을 직접 지목했다

> ■ 공공 안전 강화 및 지속 가능한 관광 모델 수립
> ☞ [데이터랩] 야간관광 현황, **관광지 집중률, 관광지 혼잡도 운영관리 매뉴얼** 등 활용 가능

오늘 그 매뉴얼을 확보해 시스템 전체의 근거로 삼은 것은 **주최 측이 기대한 방향과 정확히 일치**한다. 이 축은 유지·강화한다.

### 3중 교차검증 — 이미 확정된 구조 (v3 회의안 A)

| 단계 | 신호 | 출처 | 의미 |
| --- | --- | --- | --- |
| 선행 | 유튜브 콘텐츠 확산 | 자체 수집 (타분야 데이터) | 무엇 때문에 뜨는가 |
| **관심** | SNS 언급량 | 데이터랩 | 사람들이 말하고 있다 |
| **의도** | 내비게이션 검색건수 | 데이터랩 | 실제로 가려고 한다 |
| **실현** | 방문자 수 (이동통신) | 데이터랩 | 진짜로 갔다 |

세 지표가 모두 상승하면 실수요, **언급량만 오르고 검색이 따라오지 않으면 노이즈**로 판정한다. 행정력 낭비를 막는 기능이며, 동시에 **시간축이 정렬되어 단계별 리드타임 측정**이 가능하다.

목업의 `signal_status.cross_validation`은 아직 "이동통신 유동인구 / 유튜브 / 카드소비"로 되어 있다. 데이터 도착 시 위 3종으로 교체한다.

### 실격 관련

- **팀 인원**: 4명 확정 — 참가 구분 '팀(최대 4인)' 요건 충족 ✔

- 접수: 온라인 신청 폼 (공고 게시글 내 링크·QR)

- 발표심사 10.23(금) 서울, **신청 대표자가 발표**, 불참 시 수상 취소

| --- | --- | --- |
| `_mock` | 목업 여부 | `true`면 화면 상단에 샘플 배지를 띄운다. 목업 스크린샷이 제출물에 섞이는 사고를 막는 장치 |
| `source` | 출처 배열 | **1개 이상 필수.** 복수 데이터를 결합했으면 전부 나열 |
| `period` | 데이터가 커버하는 기간 | 예측 파일은 예측 대상 기간을 적는다 |
| `caveat` | 주의사항 | **빈 배열 금지.** 주의할 점이 없다고 판단했으면 그 근거를 문장으로 쓴다 |
| `data` | 본문 | 파일별로 다르며 각 스키마에 정의됨 |

`source`·`period`·`caveat`를 required로 건 것이 핵심이다. **"출처 없는 값은 화면에 표시되지 않도록 설계했다"가 주장이 아니라 구조적 사실이 된다.** 제출 문서의 신뢰성 항목에 그대로 쓸 수 있다.

#### 값을 마음대로 만들 수 없게 고정한 것들

스키마에서 enum으로 잠가둔 값들이다. 이 목록 밖의 값을 쓰면 검증에서 걸린다.

| 항목 | 값 | 근거 |
| --- | --- | --- |
| `alert_level` | 관심 / 주의 / 경계 / 심각 | 매뉴얼 p.10 |
| `congestion_level` | 1~5 | 매뉴얼 p.53 밀도 임계값(0.2/0.4/0.6/0.8 명/㎡) |
| `spatial_type` | 관광지 유형 4종 | 매뉴얼 p.13 |
| `content_type` | 콘텐츠 유형 9종 | 기존 6종 + 거제 실측으로 추가한 3종 (설계결정 D-01) |
| `before_after.metrics[].kpi` | KPI 11개 | 매뉴얼 p.15 3-tier |

즉 **성과 지표나 혼잡 단계를 우리가 지어낼 수 없다.** 심사에서 "이 기준은 어디서 왔나"라는 질문에 전부 쪽수로 답할 수 있다.

#### 검증

```bash
uv run python scripts/validate_data.py data/mock
```
9종 전부에 대해 필수 필드 누락, enum 위반, 타입 오류를 잡는다. 현재 전부 통과 상태다.

### 목업 JSON 9종 (`data/mock/`)

**목적**: 실데이터가 없어도 화면을 끝까지 만들 수 있게 하는 것. 일요일에 실데이터가 도착하면 **파일을 교체하는 것만으로 전체가 살아나야 한다.**

- 거제 기준. 값은 가짜지만 **자릿수·날짜 범위·항목 수는 실제와 유사**하게 맞췄다. 화면에 그렸을 때 실제와 비슷한 모양이 나오도록 한 것이다
- `forecast`는 90일치를 실제로 생성했다. 여름 성수기 곡선과 주말 가중(토 1.55배, 일 1.30배)이 들어가 있어 그래프가 평평하지 않다
- 모든 파일에 `"_mock": true`가 들어 있다
- 손으로 쓰지 않고 `scripts/gen_mock.py`로 생성했다. 시드가 고정되어 있어 재실행해도 같은 값이 나온다

**실데이터 교체 절차**
1. 실제 값을 같은 구조로 만들어 `data/prod/`에 저장 (`_mock`을 `false`로)
2. `uv run python scripts/validate_data.py data/prod`로 검증
3. 화면 코드는 수정하지 않는다 — 읽는 경로만 `mock` → `prod`로 바꾼다

이미 `content_type.json`은 이 절차를 거쳐 실데이터로 교체된 상태다.

### 에이전트② 실행 (실데이터)

#### 에이전트②가 하는 일

시스템은 5개 에이전트로 구성되며, ②는 **콘텐츠 유형 분류**를 맡는다.

```
유튜브 수집 (collection/)
        ↓
   에이전트②  ← 여기
   "이 영상이 어떤 성격의 방문 수요를 만드는가"
        ↓
content_type.json  →  AREA 2 화면 / 에이전트③ 매칭의 보조 필터
                   →  poi_mentioned가 hotspots와 조인되어 "어느 지점에 쏠리는가"
```

- **입력**: `data/raw/youtube/{지역}_{시각}.json` — 제목·설명·태그·조회수·채널
- **출력**: `data/prod/content_type.json` (스키마 `data/schema/content_type.schema.json`)
- **프롬프트**: `agents/prompts/agent2_content_type.md` v1.1

중요한 것은 **콘텐츠를 평가하는 게 아니라 사람의 이동을 예측한다**는 점이다. 같은 지역 영상이라도 만들어내는 수요의 모양이 다르다. "맛집 7곳 순회" 영상은 소수 점포에 대기열을 만들고, "수국 명소" 영상은 넓은 자연 공간으로 방문을 분산시킨다. 전자는 점포 주변 동선 관리가, 후자는 주차·진입 관리가 필요하다. 즉 **유형이 곧 대응 방식**이다.

#### 왜 LLM이어야 하는가 (키워드 필터로는 불가능하다는 실증)

이번 수집에서 결정적인 사례가 나왔다. 두 영상은 **같은 인물, 같은 시기, 같은 해시태그**를 쓰지만 성격이 정반대다.

| 영상 | 조회수 | 분류 | 이유 |
| --- | --- | --- | --- |
| 「원이의 사투리 특강」 | 1,897만 | **관광무관** | 사투리 강의 형식으로 방문할 장소 정보가 전혀 없음 |
| 「갸루와 거제에 왔습니다」 | 1,394만 | **예능·방송 노출형** | 인물의 거제 방문 자체가 콘텐츠이며 이후 확산의 기점 |

둘 다 `#거제도 #거제여행 #리센느 #원이` 태그를 달고 있다. **키워드·해시태그 기반 필터는 이 둘을 구분할 수 없다.** 반대로 "예능 영상은 노이즈"라고 일괄 제거하면, 정작 수요를 만든 진원지를 통째로 버리게 된다. 영상이 무슨 이야기를 하는지 읽어야만 구분되며, 이것이 이 단계에 LLM을 쓰는 이유다.

#### 프롬프트를 이렇게 설계한 근거

| 설계 | 근거 |
| --- | --- |
| 분류 목적을 "콘텐츠 성격"이 아니라 **"만들어내는 수요의 모양"**으로 정의 | 유형이 대응 조치로 연결되어야 의미가 있다. 매뉴얼도 유형별로 관리 방안을 달리 제시한다(p.13) |
| `예능·방송 노출형` 유형 신설 | 거제 실측에서 조회수 상위 10건 중 8건이 인물 결부 콘텐츠였다. 기존 6개 유형(맛집·포토스팟·체험·축제·자연경관·촬영지)으로는 담기지 않으면서, **확산 속도가 가장 빠르고 지점 집중도가 높은** 유형이다 |
| `관광무관` 유형 신설 + **제외 건수 표시** | 지역명만 겹치는 콘텐츠(타 지역 여행기, 지역경제 분석)를 걸러야 하지만, 조용히 버리면 "무엇을 걸렀는지" 검증할 수 없다. 필터링 과정을 드러내는 것이 신뢰성의 근거다 |
| **유형 하나만** 선택 + 타이브레이커 규칙 | 맛집과 예능이 겹칠 때 *"이 영상이 없었다면 그 점포에 갔을까"*로 판정한다. 인물 때문에 간 것이면 예능형이다. 다중 라벨을 허용하면 집계 비중이 무의미해진다 |
| **근거(evidence) 필수** — 영상의 실제 표현 인용 | 매뉴얼 조치에 쪽수를 남기는 것과 같은 원칙이다. 추측으로 쓴 근거는 금지하며, 스키마에서 `evidence`를 required로 강제한다 |
| 신뢰도 0.6 하한, **애매하면 낮게** | 제목만으로 판단이 서지 않는 종합 코스 안내 등을 억지로 분류하지 않는다. 미달분은 집계에서 빠지되 건수로 남는다 |
| `poi_mentioned` 추출 | 이 값이 `hotspots.json`과 조인되어 **"콘텐츠가 어느 지점으로 사람을 보내는가"**를 만든다. 유형 분류만으로는 현장 대응 지점을 특정할 수 없다 |
| `sentiment` 병기 | 유형 축만으로는 과열 징후를 담을 수 없다. 「거제 바가지, '확답' 듣고 왔습니다」(19.6만)는 유형상 예능 노출형이지만 **sentiment=부정**으로 잡혀 과열 신호가 된다 |

#### 남은 한계

1. **제목·설명·태그 텍스트만 사용했다.** 영상 내용을 시청해 검증하지 않았고, 자막(captions)도 쓰지 않았다. 댓글도 수집 옵션은 있으나 이번엔 쓰지 않았다.
2. **검색 결과 상위만 수집**해 소규모 채널이 과소 대표된다. 조회수는 수집 시점 기준으로 계속 변동한다.
3. **분류 결과가 스크립트의 상수 표에 들어 있다.** 재실행 시 사람이 표를 교체해야 한다. LLM API 키가 있으면 자동화할 수 있으나, 현재는 판정 근거가 코드에 그대로 보인다는 장점과 맞바꾼 상태다.

### 개발 환경

Python 환경은 **uv**로 통일했다. 가상환경 생성·의존성 설치가 한 명령이고, `uv.lock`이 커밋되어 있어 팀원 모두가 **정확히 같은 버전**을 쓴다.

#### 처음 받았을 때 (팀원용 세팅 절차)

```bash
git clone -b agents https://github.com/j2nii/tourism-early-warning.git
cd tourism-early-warning

uv sync                      # 가상환경 생성 + 의존성 설치 (uv가 없으면 아래 참고)

cp .env.example .env         # 키가 필요한 작업을 할 경우에만
# .env를 열어 YOUTUBE_API_KEY 값을 채운다
```

uv가 설치되어 있지 않으면 (PowerShell):
```powershell
irm https://astral.sh/uv/install.ps1 | iex
```

동작 확인:
```bash
uv run python scripts/validate_data.py data/mock    # "전체 통과"가 나오면 정상
```

#### 주의

- **`.env`는 절대 커밋하지 않는다.** gitignore에 등록되어 있으나, 키를 다른 파일에 붙여넣지 않도록 주의할 것
- 실행은 `python` 대신 **`uv run python`**을 쓴다. 가상환경을 따로 활성화할 필요가 없다
- 스크립트 출력은 UTF-8로 강제되어 있다. 윈도우 CMD에서 한글이 깨지면 PowerShell이나 Git Bash를 쓸 것
- 윈도우 CMD에는 `grep`·`head` 같은 명령이 없다. README의 bash 예시는 **Git Bash**에서 실행할 것

### 역할1 (데이터 수집·검증) — 중복 작업 방지

```bash
uv run python collection/youtube_collect.py --region 여수 --comments --days 220
```

- 검색어는 `{지역} 여행` / `{지역} 가볼만한곳` / `{지역} 맛집` 3종으로 고정되어 있다 (설계결정 D-06). 지역명만 바꾸면 8곳에 그대로 적용된다

- **쿼터가 자동 계산되어 출력**된다. 하루 10,000 units, 검색 1회당 100 units. 오늘 사용량은 605 units
- 출력은 `data/raw/youtube/{지역}_{시각}.json`. W1 파일명 규칙(`{지역}_{항목}_{기간}`)과 다르므로 필요하면 맞춰 바꾸면 된다

거제는 이미 수집·분류까지 끝났다. **나머지 7곳만 돌리면 된다.**

   - `data.assessment`: 예상 상황 유형과 **매뉴얼 범위 밖 이슈**(바가지 등). AREA 3 상단에 짧게 띄우면 "AI가 정책을 만들지 않는다"를 보여 주는 장면이 된다
   - `signal_status.cross_validation[].stage`: `관심` / `의도` / `실현`
6. **`briefing.json`이 10번째 파일로 생겼다** (`data/mock/`, `data/prod/` 모두). AREA 3 상단 브리핑
   - `paragraphs` 3개(현재 상황 → 예상 전개 → 권고 조치) 순서 고정, 합계 400~600자
   - `facts`에 문장 속 숫자의 출처가 있다 → **수치 옆 출처 툴팁**으로 쓰면 "출처 없는 값은 없다"가 화면에서 보인다
   - `actions`는 권고 조치 1~3건과 체크리스트 id — 체크리스트 항목으로 연결할 때 쓴다

인계 메시지 초안: `docs/meeting-notes/인계메시지_0912.md` §3

#### 데이터 로더는 이렇게 두면 교체가 한 줄이 된다

```js
// src/data/loadData.js
const USE_PROD = import.meta.env.VITE_USE_PROD === 'true';

export async function loadData(name) {
  const dir = USE_PROD ? 'prod' : 'mock';
  const res = await fetch(`/data/${dir}/${name}.json`);
  return res.json();          // { _mock, source, period, caveat, data }
}
```

실데이터 도착 시 바꾸는 것은 환경변수 하나뿐이다. 파일별로 개별 전환이 필요하면 `name`에 따라 분기해도 된다 (`content_type`은 이미 prod가 있다).

#### 공통 컴포넌트 3개

| 컴포넌트 | 하는 일 |
| --- | --- |
| `<SourceBadge source period />` | 출처·기관·조회일·기간 표시. **모든 데이터 블록에 붙인다** |
| `<CaveatNote caveat />` | 주의사항 목록. 접어두되 항상 접근 가능하게 |
| `<MockBanner show={_mock} />` | `_mock: true`일 때 화면 상단 고정 배너 |

`MockBanner`가 특히 중요하다. 목업 화면을 스크린샷으로 제출물에 넣는 사고를 막는 장치이며, 심사에서 "이 화면이 실데이터인지 어떻게 아는가"에 대한 답이기도 하다.

#### 오늘의 우선순위

1. **Vercel 배포 URL 확보** — 빈 화면이어도 좋다. URL이 오늘 존재해야 한다
2. 데이터 로더 + 공통 컴포넌트 3개
3. 라우팅 + AREA 0~4 빈 페이지 5개
4. **AREA 0 관제 대시보드** — 시연 첫 화면이자 대표 스크린샷이므로 여기만 완성도를 올린다
5. 나머지 4개 화면 골격 (클릭이 끝까지 되는 수준)

디자인 다듬기는 이번 주 작업이 아니다. 심사 대상은 서식4 문서이지 웹이 아니다.

### 역할1·2 (매뉴얼 구조화 — 수집 작업 끝난 뒤)

태그 체계 설계와 **35건(p.50·p.20①②·p.13·p.39·p.37)은 역할4가 채웠다** — 에이전트③ 테스트에 필요했기 때문이다. 남은 것은 **나머지 범위를 같은 형식으로 채우는 작업**이며, 데이터 수집이 일단락된 뒤 분담한다.

**이 작업의 결과물이 시스템의 검색 인덱스가 된다.** 매뉴얼에 흩어진 조치를 한 건씩 레코드로 만들면, 시스템이 "지금 상황(경보 단계 + 공간 유형 + 방문객 특성)에 해당하는 조치"만 골라 화면에 띄울 수 있다. 항목 하나하나에 붙는 쪽수가 곧 **"AI가 정책을 창작하지 않았다"는 증거**다.

1. `manual/README_태그체계.md` 읽기 — 필드 설명과 값 목록이 전부 정리되어 있다
2. `manual/checklist_items.json`에 이미 35건이 있다. **같은 파일에 이어서** 추가한다 (id 대역은 README 표 참고)
3. PDF에 텍스트 레이어가 없다 — 작은 글씨는 **확대해서 판독**할 것 (p.20의 "우천"이 원본 크기로는 "주전"처럼 보인다)
4. 검증: `uv run python scripts/validate_manual.py`

남은 범위와 id 대역은 README에 표로 정리되어 있다 (p.20 ③~⑦ 20건, p.18~19, p.35, p.38, p.40).

**중요**: 조치 문장을 요약하거나 다듬지 말 것. 매뉴얼은 공공누리 4유형(변경금지)이며, 원문 그대로 옮기고 쪽수를 남기는 것이 이 프로젝트의 신뢰성 근거다.

| 결정 | 이유 |

| `data/prod/*.json`은 gitignore 예외로 추적 | 웹이 직접 읽는 제품이며 건당 수 KB |

## 용어

| 용어 | 뜻 |
| --- | --- |
| **경보 단계** (`alert_level`) | 관심·주의·경계·심각. 우리 시스템이 내리는 판단 |
| **혼잡도 단계** (`congestion_level`) | 1~5. 밀도(명/㎡) 기준의 측정 등급. 매뉴얼 p.53 |
| **공간 유형** (`spatial_type`) | 관광지의 물리적 성격 4분류. 매뉴얼 p.13. 조치를 결정한다 |
| **콘텐츠 유형** (`content_type`) | 콘텐츠가 만드는 수요의 성격 9분류. 공간 유형과 **다른 축**이다 |
| **상황 유형** (`situation_type`) | 혼잡이 어떤 모양으로 터지는가 4분류 — 유입 급증형·병목 정체형·안전 위험형·민원 급증형. 매뉴얼 p.39 |
| **발동 / 대기** | 체크리스트 항목의 상태. 대기는 경보 단계는 맞지만 현재 혼잡도가 조건에 못 미친 현장 조치 (D-07) |
| **봉투(envelope)** | 모든 JSON이 공유하는 껍데기 (`source`/`period`/`caveat`/`data`) |
| **3중 교차검증** | 출처가 다른 독립 신호 3개의 합의로 경보를 올리는 방식 |
| **핫존-데드존** | 같은 지역 안에서 사람이 몰리는 곳과 비는 곳. 격차는 지니계수로 측정 (매뉴얼 Tier1 KPI) |
