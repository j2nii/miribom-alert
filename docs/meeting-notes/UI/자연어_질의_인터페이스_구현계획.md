# 자연어 질의 인터페이스(채팅) 구현 계획

> 2026-09-17 작성 · 관련 문서: [프론트구조_기능조사_및_에이전트연동계획.md](./프론트구조_기능조사_및_에이전트연동계획.md)

## Context

이전 조사(`프론트구조_기능조사_및_에이전트연동계획.md`)에서 "자연어 질의 인터페이스"가 v3 문서 §4에만 설계로 존재하고 프론트에는 코드가 전무하다는 것을 확인했다. 이번 계획은 그 기능을 실제로 구현하는 것이다.

**확인된 요구사항** (사용자 답변 기준):
- 사용자는 개발자가 아니라 **지자체 공무원**. 채팅은 관광 데이터(9종 JSON + 매뉴얼 체크리스트)에 대한 질문에 답하는 용도. 프로젝트 내부 문서(회의록, 설계결정.md 등)는 참조 대상이 아니다.
- 이미 연결된 데이터/에이전트 산출물을 **재사용**하거나 **직접 조회**하는 방식을 원함 — 새로운 콘텐츠를 창작하는 게 아니라 기존 JSON 계약을 조회해 답하는 구조.
- UI는 **AREA0 중심 배치**, 스크롤을 내리면 **floating 위젯으로 전환**되어 따라오고, **원하는 위치로 드래그 이동 가능**하며, 접었을 때는 버튼으로 다시 열 수 있어야 한다.

**전용 에이전트는 없음**: 5개 에이전트(①~⑤) 중 이 기능을 위한 것은 없다. v3 문서 §4의 "자연어 질의 인터페이스"는 별도 오케스트레이션 레이어로, 9종 JSON 계약(`data/mock|prod/*.json`)을 도구처럼 조회하는 구조다.

**RAG가 필요한가 — 아니오.** 참조 대상이 9종의 작고 이미 구조화된 JSON 파일(+ 매뉴얼 체크리스트도 그중 `checklist.json`)이라, 벡터 임베딩·유사도 검색이 필요한 대용량 비정형 텍스트 코퍼스가 아니다. 대신 **진짜 tool-calling(함수 호출)**을 쓴다: 9종 JSON을 각각 하나의 "도구"로 노출하고, LLM이 질문에 필요한 도구를 스스로 선택해 호출하면 서버가 해당 JSON을 그대로 가져와 돌려주고, 모델이 그 사실만으로 최종 답을 생성한다. 이는 v3 문서가 원래 그리던 "8개 `get_*` 도구 호출" 설계를 문자 그대로 구현하는 것이다.

**Upstage Solar의 tool-calling 지원 확인됨** (공식 문서 `console.upstage.ai/docs/guides/function-calling`, `console.upstage.ai/api/chat` 기준, 웹 검색으로 교차 확인):
- Solar Pro 4(현재 `briefing.js`가 쓰는 모델)는 OpenAI Chat Completions와 동일한 `tools` / `tool_choice` 파라미터를 지원 ("Solar Pro 4 accepts tools and tool_choice for function calling")
- `tool_choice`: `none`(기본, tools 없을 때) / `auto`(기본, tools 있을 때, 모델이 직접 호출 여부 판단) / `required`(반드시 하나 이상 호출) / 특정 함수 지정도 가능
- 병렬 함수 호출(`parallel_tool_calls`) 지원 — 한 번에 여러 도구를 동시에 호출 가능(예: "상황 어때?" 질문에 `get_signal_status`+`get_forecast` 동시 호출)
- 이미 프로젝트에 있는 `openai` npm SDK(현재 `briefing.js`가 씀)가 이 파라미터들을 네이티브로 지원하므로 별도 클라이언트/파서 구현 불필요

즉 당초 계획했던 "LLM에게 JSON 배열을 텍스트로 뱉게 하는" 수작업 우회가 필요 없다 — 표준 OpenAI 호환 tool-calling 루프로 구현한다.

## 아키텍처

```
[ChatWidget.jsx] --POST { region, question, history }--> [web/api/query.js]
                                                                │
                                          1) 1차 completions.create({ tools, tool_choice: "auto" })
                                             모델이 필요한 dataType에 해당하는 tool_call(들)을 반환
                                             (예: get_signal_status, get_forecast 동시 호출 가능)
                                                                │
                                          2) 서버가 각 tool_call에 대해 해당 JSON envelope를
                                             절대 URL로 fetch (/mock|prod/*.json) 후
                                             role:"tool" 메시지로 대화에 추가
                                                                │
                                          3) 2차 completions.create() (tools 없이)
                                             — facts만 근거로 최종 자연어 답변 생성
                                                                │
                                        <-- { answer, usedDataTypes[], envelopes{} } --
```

모델이 도구 호출 없이 바로 답할 수 있다고 판단하면(예: 인사말, 범위 밖 질문) 1차 호출에서 `tool_calls` 없이 바로 텍스트가 오므로 2차 호출 없이 그대로 반환한다.

기존 `web/api/briefing.js` 패턴(Upstage Solar, `UPSTAGE_API_KEY`, `openai` SDK)을 그대로 재사용한다 — 새 API 키/제공자 불필요.

## 신규/수정 파일

### 1. `web/api/_lib/dataManifest.js` (신규)
`web/src/data/manifest.js`와 동일한 9개 dataType → `{mock,prod}` 경로 테이블의 **서버 전용 복제본**. 이유: `manifest.js`는 `import.meta.env.VITE_USE_PROD`(Vite 빌드 타임 치환)에 의존하는데, Vercel Node 함수는 Vite를 거치지 않으므로 이 값을 읽을 수 없다. 대신 `process.env.VITE_USE_PROD`를 그대로 읽는 9줄짜리 표로 복제한다. 파일 상단에 `manifest.js`와 동기화하라는 주석을 남긴다 (기존 코드 스타일과 동일).

### 2. `web/api/query.js` (신규, `briefing.js` 패턴 그대로)
- `POST { region, regionLabel, question, history }` 받음
- **도구 스키마 정의**: 9개 dataType(=9종 JSON 계약) 각각을 파라미터 없는 OpenAI `tools` 함수로 정의 — `get_signal_status`, `get_forecast`, `get_visitor_profile`, `get_hotspots`, `get_content_type`, `get_checklist`, `get_precedent`, `compare_before_after`(→`before_after.json`), `get_timeline`. 설명은 v3 문서 §4 도구 표의 한글 설명을 그대로 사용. region은 모델에게 파라미터로 받지 않고 요청 바디의 `region`을 서버가 고정 사용(모델이 다른 지역을 지어내지 못하도록).
- **1차 호출**: `client.chat.completions.create({ model, messages: [system, ...history, user], tools, tool_choice: "auto", parallel_tool_calls: true })`
- **도구 실행**: 응답에 `tool_calls`가 있으면 각각에 대해 `_lib/dataManifest.js`로 경로를 찾고 `https://${req.headers["x-forwarded-host"] ?? req.headers.host}/mock|prod/*.json`을 서버에서 fetch — 클라이언트 `loadData.js`가 읽는 것과 동일한 정적 파일을 그대로 재사용(중복 구현 없음). 해당 region에 파일이 없으면(`unsupported`) 그 사실 자체를 도구 응답으로 반환. 원본 assistant `tool_calls` 메시지 + 각 `role:"tool"` 메시지를 대화에 추가.
- **2차 호출**(도구가 하나라도 실행된 경우만): 동일 메시지 배열로 `tools` 없이 다시 호출해 최종 자연어 답변을 받음. 시스템 프롬프트로 다음을 강제 — 도구 결과 JSON 사실에만 근거, 수치엔 출처, 없는 조치·수치 창작 금지, 데이터가 없으면 "확인 불가"라고 명시, 공무원 대상 문어체, 2~4문장 내외.
- `tool_calls`가 처음부터 없으면(모델이 도구 없이 답 가능하다고 판단) 1차 응답의 텍스트를 그대로 사용.
- `history`(최근 6턴 이하)를 매 요청에 포함해 후속 질문("그럼 주말은?") 처리.
- 응답: `{ answer, usedDataTypes: [...], envelopes: {...} }` — `envelopes`는 프론트가 `SourceBadge`/`CaveatNote`로 출처를 표시할 수 있도록 실제 호출된 도구의 envelope만 포함.
- **안전망**: tool-calling 자체가 실패하거나(네트워크, 파싱 오류) 예상과 다른 응답 형식이 오면 9종 전부를 직접 fetch해 컨텍스트에 통째로 넣는 단일 호출로 폴백(데이터가 작아 비용 문제 없음) — 배포 초기 안정성 확보용.
- 에러 처리: `briefing.js`와 동일하게 키 미설정(503)/모델 오류를 구분해 응답. 브리핑과 달리 규칙 기반 폴백 답변기는 만들지 않음(개방형 질의라 의미 있는 결정론적 대체가 없음) — 프론트에서 "지금은 답변할 수 없습니다" 정도의 에러 상태만 표시.

### 3. `web/src/components/common/ChatWidget.jsx` (신규)
- 메시지 목록 + 입력창 + 전송 버튼 (기존 `btn-primary`/`btn-ghost` 클래스 재사용)
- 답변 메시지에는 `usedDataTypes`를 작은 배지로, `envelopes`가 있으면 기존 `SourceBadge`/`CaveatNote` 컴포넌트를 재사용해 출처 표시 (새 컴포넌트 만들지 않음)
- **Docked/Floating 상태 전환**: AREA0 안에 sentinel(`<div ref>` 높이 1px)을 두고 `IntersectionObserver`로 관찰 — sentinel이 뷰포트를 벗어나면 위젯이 `position: fixed` 플로팅 모드로 전환, 다시 들어오면 인라인(docked) 모드로 복귀
- **Floating일 때만 드래그 가능**: 헤더 영역에 pointer 이벤트(`onPointerDown/Move/Up`)로 위치(top/left) 갱신, 뷰포트 경계로 clamp. 위치는 `localStorage`에 시도적으로 저장(실패해도 무시 — 필수 아님, 새로고침 편의용)
- **접힌 상태**: floating이고 collapsed면 원형 토글 버튼만 표시 → 클릭 시 패널 펼침
- props: `region`, `regionLabel` (App.jsx의 기존 `region` state 재사용)

### 4. `web/src/pages/Area0Dashboard.jsx` (수정)
- 상단에 `<ChatWidget region={region} regionLabel={...} />`와 sentinel 앵커 삽입. `region` 라벨은 `manifest.js`의 `REGIONS` 배열에서 찾아 전달(기존 `Area1SignalScan.jsx`가 이미 이 배열을 쓰는지 확인 후 같은 방식 재사용).

### 5. `web/src/index.css` (수정)
- 기존 스타일 관례(`.panel`, `.btn-primary`, `.source-badge` 등)를 따라 `.chat-widget`, `.chat-widget--floating`, `.chat-widget__toggle`, `.chat-message` 등 클래스 추가. 새 CSS 프레임워크/라이브러리 도입 없음.

## 명시적으로 하지 않는 것

- 벡터 DB/임베딩 기반 RAG 파이프라인 구축 — 데이터 규모상 불필요
- 프로젝트 내부 문서(회의록, 설계결정.md 등) 검색 — 사용자가 범위에서 제외함
- 새로운 LLM 제공자/키 추가 — 기존 `UPSTAGE_API_KEY`/Upstage Solar 재사용
- 결정론적 규칙 기반 폴백 답변기(브리핑과 달리 개방형 질의라 의미 있는 템플릿을 만들 수 없음) — 실패 시 명확한 에러 상태만 표시
- 드래그 라이브러리 등 신규 npm 의존성 추가 — 순수 pointer 이벤트로 구현

## 검증 방법

1. `cd web && npm run dev` (Vite) 로 프론트 기동. `/api/query`는 Vercel 함수라 로컬 `vite dev`에서는 동작하지 않으므로(기존 `briefing.js`와 동일한 제약), **`vercel dev`로 기동**해 실제 API 응답을 확인해야 함 — 이 제약을 README/팀 문서에도 한 줄 남긴다.
2. 거제(geoje) 지역에서 "지금 우리 지역 상황 어때?", "이번 주말 방문객 얼마나 예상돼?" 같은 질문을 보내 응답의 `usedDataTypes`로 모델이 올바른 도구(예: `get_signal_status`+`get_forecast` 병렬 호출)를 선택했는지, 답변에 출처가 붙는지 확인
3. 충주(chungju)처럼 데이터가 일부만 있는 지역에서 없는 dataType을 물었을 때 "확인 불가"로 정직하게 답하는지 확인 (수치 창작 금지 검증)
4. AREA0에서 스크롤을 내려 AREA1~4로 이동했을 때 위젯이 floating 토글 버튼으로 바뀌는지, 펼친 뒤 드래그로 위치를 옮길 수 있는지, 다시 AREA0 상단으로 스크롤하면 docked로 복귀하는지 브라우저에서 직접 확인
5. `UPSTAGE_API_KEY` 미설정 상태를 가정해 에러 상태 UI가 깨지지 않는지 확인
