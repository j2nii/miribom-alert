## 1. 결론 — SurgeLens를 뼈대로, 노칫 얼럿을 흡수

### 두 안의 차이

> **SurgeLens는 논문이고, 노칫 얼럿은 앱이다.**

| | SurgeLens | 노칫 얼럿 |
| --- | --- | --- |
| 최종 산출물 | **발견** — "바이럴과 방문급증 사이 N주 시차" | **도구** — 담당자가 매일 켜두는 관제 화면 |
| 시간 방향 | 과거를 되짚음 (사후 규명) | 현재를 감시함 (상시 관제) |
| 다루는 원인 | 바이럴 하나, 깊게 | 5가지 트리거, 넓게 |
| 성과 증명 | 백테스트 숫자 (리드타임·적중률) | 실사용 가치 |

### 결정 근거

**① 성과 증명 방식이 결정적**

배점 30%인 효과성·성과창출도에서, 노칫 얼럿은 5주 안에 지자체 도입 실적을 만들 수 없어 계획만 제출하게 된다. SurgeLens는 **사용자가 0명이어도 숫자가 나온다.** 작년 대상작(강진군)이 방문자 43만 명 증가·소비 69억 원이라는 실측 숫자로 받았다는 점을 감안하면, 숫자 없는 제안서는 상위권이 어렵다.

**② 팀 역량 배분** — 넷 다 비슷한 수준이면 넷 다 분석 가능. 분석 중심이면 네 명이 동시에 기여한다.

**③ 노칫 얼럿 자산이 버려지지 않음**

| 노칫 얼럿 자산 | 통합 후 위치 |
| --- | --- |
| 5가지 트리거 사례 (성수동·망원·경주·북촌·양양) | 문제 정의 |
| 공식 혼잡도 운영관리 매뉴얼 매칭 | 서비스 핵심 기능 |
| 관제 대시보드 | 서비스 기본 화면 |
| Human-in-the-Loop 설계 | 서비스 설계 원칙 |
| 사용자 시나리오 6종 | 발표 자료 |

## 2. 통합안 구조

```
[문제 정의]  5가지 트리거로 문제의 크기 제시        ← 노칫 얼럿 사례 자산
      ↓
[본론 70%]  거제 등 사례의 lead-lag 규명           ← SurgeLens 방법론
      ↓
[제언 30%]  조기경보 + 공식 매뉴얼 매칭 서비스      ← 노칫 얼럿 기능 + 프로토타입
```

7:3은 **제출 문서의 서술 비중**이지 개발 비중이 아니다.

### 문제 정의 문장

> 감지는 담당자의 감각에 의존해 재현되지 않고, 감지한 뒤에도 무엇을 할지 정하는 데 시간이 걸린다. 우리는 감지를 데이터로 시스템화하고, 대응을 공식 매뉴얼로 즉시 매칭한다.

## 3. 데이터 활용 확장 — 담당자의 질문 흐름

데이터를 많이 쓰는 것 자체는 목적이 아니다. **담당자가 순서대로 던지는 질문에 각 데이터가 답하는 구조**로 설계한다.

```
① 지금 뜨고 있나 → ② 진짜인가 → ③ 얼마나 커지나 → ④ 누가 오나
→ ⑤ 어디로 몰리나 → ⑥ 뭘 준비하나 → ⑦ 효과 있었나
```

### 채택 — 구현 필수 (5종)

**A. 3중 교차검증 신호등** (질문 ②)

| 단계 | 데이터 | 의미 |
| --- | --- | --- |
| 관심 | SNS 언급량 | 사람들이 말하고 있다 |
| 의도 | 목적지 유형별 검색량 (내비게이션) | 실제로 가려고 한다 |
| 실현 | 방문자수 추이 (이동통신) | 진짜로 갔다 |

세 지표가 모두 상승하면 실수요, 언급량만 오르고 검색이 따라오지 않으면 노이즈로 판정. 행정력 낭비를 막는 기능.

**B. 향후 90일 방문자 예측 연동** (질문 ③)

데이터랩이 AI 기계학습으로 향후 90일 방문자 수를 예측 제공. 조기경보가 "떴다"에서 끝나지 않고 **"7월 셋째 주 정점, 평시 대비 N배 예상"** 까지 제시.

**C. 요일별 집중률 예측** (질문 ③)

향후 5주간 날짜별 방문자 비율 예측값 제공. **인력·예산 배치의 직접 근거**가 된다.

> B·C가 이번 확장의 핵심. 조기경보의 성격이 "경고"에서 "예보"로 승격된다.

**D. 방문객 유형 프로파일** (질문 ④)

| 축 | 데이터 | 대응 함의 |
| --- | --- | --- |
| 연령·성별 | 방문자 성/연령 분포 | 20대 급증 → 야간 소음·주차 |
| 출발지 | 방문자 거주지 분포 | 수도권 유입 → 대중교통 증편 |
| 이동 거리 | 거리별 방문자 분포 | 원거리 비중↑ → 숙박 수요 발생 |
| 소비 성향 | 관광소비 유형 분포 (하위유형) | 식음료 편중 → 위생·바가지 점검 |
| 동반 형태 | 동반유형 언급량·키워드 | 가족 단위 → 안전·편의시설 |

이 매핑이 정책 브리핑의 입력값이 된다.

**E. 급증 지점 랭킹** (질문 ⑤)

시군구 단위로는 "거제가 뜬다"까지밖에 말할 수 없다. 담당자가 필요한 건 "어디에 인력을 보낼까"다.

- 인기 관광지 (현지인/외지인/전체 구분)
- 주요 유료관광지점 입장객 수
- 내국인 관심 관광지 (구석구석 조회 상위)

> 현지인 순위는 그대로인데 **외지인 순위만 급등한 지점**이 관광객 쏠림이 실제 발생한 곳이다.

### 채택 — 가능하면 (3종)

**F. 유사 지역 선례 제시** (질문 ⑥)
데이터랩이 관광진단지표·방문자특성·관광소비·검색특성 기준으로 유사 지역 3곳씩 자동 추천. "우리와 비슷한 A시가 같은 상황에서 이렇게 대응했다"는 정보가 브리핑 설득력을 크게 높인다.

**G. 조치 전후 비교 리포트** (질문 ⑦)
조치 시점 기준으로 방문자·소비·체류시간 변화를 자동 비교. 거제의 실제 조치(6.12 바가지 캠페인) 전후를 비교하면 백테스트 성과가 하나 더 확보된다. **효과성 배점에 직접 기여.**

**H. 유입·유출 파급 예측** (질문 ⑤)
내비게이션 출발·도착지 기반. "거제가 뜨면 통영·고성에도 파급된다"는 인접 지자체 공동 대응 제언으로 이어진다. 파급력 항목 강화.

### 문서에만 기술 (확장 계획)

- 계절성 기저선 대비 판정 — 성수기와 바이럴 구분
- 소비 데이터로 기회이익 계량
- 중심 관광지 기반 동선 병목 예측
- 숙박 수요 급증 감지 (당일치기 → 1박 전환)
- 지역관광진단 5개 지표 시계열 추적

## 4. 에이전트 설계

### 설계 원칙 — 어디에 쓰지 않을지부터 정한다

LLM은 **비정형 입력, 다단계 판단, 자연어 출력** 세 조건 중 하나 이상에 해당할 때만 쓴다. 규칙으로 되는 것을 LLM으로 처리하면 느리고 불안정하며, 심사에서도 "LLM을 장식으로 썼다"고 평가된다.

| 규칙으로 처리 (LLM 미사용) | 이유 |
| --- | --- |
| 3중 교차검증 판정 | 세 지표 상승 여부는 조건문 |
| 급상승 임계치 판정 | 통계적 기준으로 결정 |
| 방문자 예측 | 데이터랩이 이미 제공 |
| 급증 지점 랭킹 | 정렬 연산 |
| 조치 전후 수치 비교 | 산술 연산 |

> **이 경계를 문서에 명시하는 것 자체가 강점이다.** "필요한 곳에만 LLM을 썼다"는 서술은 기술적 판단력의 근거가 된다.

### 에이전트 5종

**① 타임라인 추출 에이전트** — 본론 지원

뉴스·보도자료·공고에서 **바이럴 기점 / 방문자 급증 언급 / 행정 대응 시점**을 구조화 추출해 사례별 대응 시차 타임라인을 자동 구축.

- **왜 LLM인가**: 기사 문구가 제각각이라 규칙 기반 추출이 불가능
- **효과**: 사례마다 기사를 수작업으로 뒤지는 작업을 대체 → 백테스트 사례 수를 늘릴 수 있음
- **도구**: 웹·뉴스 검색, 페이지 fetch, 날짜·지명 정규화
- **출력**: 사례별 타임라인 JSON

**② 콘텐츠 유형 분류 에이전트** — 데이터 활용안 D 지원

유튜브 영상의 제목·썸네일·자막·댓글을 멀티모달로 분석해 **맛집형 / 팝업형 / 자연경관형 / 야간형** 등으로 자동 분류.

- **왜 LLM인가**: 영상·이미지·텍스트 복합 입력. 데이터랩만으로는 "무엇 때문에 뜨는지"를 알 수 없음
- **효과**: 유형에 따라 필요한 조치가 완전히 달라짐 (야간형 → 소음·조명, 맛집형 → 위생·대기줄)
- **도구**: YouTube Data API, 자막·댓글 조회, 멀티모달 LLM
- **출력**: 유형 라벨 + 판단 근거

> 이 에이전트가 **데이터랩이 못 하는 부분을 정확히 메운다.** 데이터랩은 "얼마나 오는가"를 알려주지만 "왜 오는가"는 모른다. 융복합 가점 요인이기도 하다.

**③ 매뉴얼 매칭 에이전트** — 서비스 핵심

한국관광공사 '지속가능한 관광지 혼잡도 운영관리 매뉴얼'에서 현재 상황(단계 · 콘텐츠 유형 · 방문객 프로파일 · 급증 지점)에 맞는 대응 시나리오와 체크리스트 항목을 선별.

- **왜 LLM인가**: 상황 조건이 다차원이라 규칙 테이블로 전부 커버 불가. 매뉴얼 원문에서 의미적으로 맞는 항목을 찾아야 함
- **핵심**: AI가 정책을 **창작하지 않는다.** 공식 문서에서 선별할 뿐
- **도구**: 구조화된 매뉴얼 체크리스트(역할 4 산출물), 유형·프로파일 조회
- **출력**: 선별된 체크리스트 + 각 항목의 매뉴얼 근거 위치

> "AI가 만든 정책을 믿을 수 있나"라는 심사 질문에 대한 완결된 답변.

**④ 선례 조사 에이전트** — 데이터 활용안 F 지원

데이터랩이 추천한 유사 지역이 과거 비슷한 상황에서 실제로 어떤 조치를 취했는지 뉴스·보도자료에서 찾아 요약.

- **왜 LLM인가**: 검색 → 관련성 판단 → 요약의 다단계 작업
- **효과**: 매뉴얼 체크리스트에 **실제 선례**가 붙어 설득력이 달라짐
- **도구**: 데이터랩 유사 지역 조회, 웹 검색, 요약
- **출력**: 유사 지역별 조치 사례 카드

**⑤ 브리핑 생성 에이전트** — 최종 출력

②③④의 결과와 수치 데이터를 받아 **담당 부서에 전달 가능한 공문 형식 문서**로 작성.

- **왜 LLM인가**: 구조화 데이터 → 자연어 문서 변환(data-to-text)
- **한정**: 내용을 창작하지 않고 주어진 근거만 문장으로 재구성
- **출력**: 공문형 브리핑 (복사 / 파일 저장 / 재작성)

### 자연어 질의 인터페이스

담당자가 "지금 우리 지역 상황 어때?"라고 물으면 여러 데이터를 조회해 답하는 대화형 진입점. 위 에이전트들과 데이터 조회 함수를 도구로 호출한다.

| 도구 | 반환 |
| --- | --- |
| `get_signal_status` | 현재 단계, 3중 교차검증 결과 |
| `get_forecast` | 90일 예측, 요일별 집중률 |
| `get_visitor_profile` | 성/연령·거주지·거리·소비·동반유형 |
| `get_hotspots` | 급증 지점 랭킹 (현지인/외지인 구분) |
| `get_content_type` | 콘텐츠 유형 분류 결과 |
| `get_checklist` | 매칭된 매뉴얼 체크리스트 |
| `get_precedent` | 유사 지역 선례 |
| `compare_before_after` | 조치 전후 변화 |

**공통 반환 규격**: `data`, `source`, `period`, `caveat` 필수. `source`가 없으면 답변에 인용하지 않는다.

### 검증 장치

**편향·인과성 자체 검증**

생성된 브리핑이 특정 지역·업종에 편향되지 않는지 자체 점검. 지역·업종별 층화 비교, 반사실(counterfactual) 입력 테스트, 원본/변형 응답 대조.

> 유사 프로젝트가 대체로 갖추지 않는 층이다. 발표에서 반드시 나올 "AI 판단을 신뢰할 수 있나"에 대한 선제 답변.

**Human-in-the-Loop**

모든 브리핑은 초안이며, 최종 판단과 실행은 담당 공무원이 확인·수정 후 승인한다.

## 5. 화면 구성

| 화면 | 내용 | 데이터·에이전트 |
| --- | --- | --- |
| **AREA 0 · 관제 대시보드** | 관할 구역 위험도 랭킹, 매일 여는 기본 화면 | E(지점 랭킹) + B(예측) |
| **AREA 1 · 신호 스캔** | 단계 판정 + 근거 + 타임라인 + 대응 시차 | A(교차검증) + B·C(예측) + 에이전트① |
| **AREA 2 · 콘텐츠·유형** | 유튜브 / SNS / 검색 장소 / **방문객 유형** 4탭 | D(프로파일) + H(파급) + 에이전트② |
| **AREA 3 · 정책 브리핑** | 매뉴얼 체크리스트 + 선례 + 공문 초안 | F(선례) + 에이전트③④⑤ |
| **AREA 4 · 성과 리포트** | 조치 전후 비교, 진단 지표 추적 | G(전후 비교) |

AREA 2에 "방문객 유형" 탭 추가, AREA 4 신설.

## 6. 기술 스택

| 영역 | 선택 |
| --- | --- |
| 프론트 | React (기존 프로토타입과 동일 계열) |
| 분석 | Python / pandas |
| 연결 | 분석 결과를 **정적 JSON**으로 산출 → 프론트에서 로드 |
| 배포 | Vercel 등 정적 호스팅 |
| 외부 API | YouTube Data API v3, LLM API |

**핵심 설계 원칙**: 분석과 프론트를 JSON으로 분리한다. 분석 담당이 JSON을 떨구면 프론트가 읽는 구조여야 두 작업이 서로 막지 않는다. **JSON 스키마를 이번 주에 먼저 확정한다.**

에이전트 출력도 동일하게 JSON으로 떨어뜨려, 데모에서는 사전 생성된 결과를 로드하고 실시간 호출은 일부 화면에만 적용한다. (안정성 확보 및 API 비용 관리)
