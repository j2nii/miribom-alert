## D-01. 콘텐츠 유형에 `코스·일정형`을 추가한다

### 결정
`content_type` enum에 **`코스·일정형`**을 추가해 9종으로 운영한다.

> 예능·방송 노출형 / 맛집형 / 포토스팟형 / 체험·액티비티형 / 축제·이벤트형 / 자연경관형 / 드라마·영화촬영지형 / **코스·일정형** / 관광무관

판별 기준: **시간 순서가 콘텐츠의 구조인 것.** "1박 2일", "당일치기", "N일 코스"처럼 일정이 뼈대이고 지점들이 순서대로 나열된다.

인물 추천 목록("원이 추천 맛집 7곳")과 헷갈리기 쉬운데, 이쪽은 **순서가 아니라 목록**이다. 순서를 바꿔도 콘텐츠가 성립하면 코스형이 아니다.

### 근거
오늘 수집한 59건 중 2건이 이 성격이었고, 둘 다 유형 특정 실패로 신뢰도 0.5 미만 처리되어 집계에서 빠졌다.

- 「올여름 국내 여행지 1순위 '거제' 여행의 모든 것」 24.8만 회
- 「현지인 추천 1박 2일 거제 여행 코스」 7.9만 회 (설명에 관광지 50곳 언급)

이들을 버리면 **여행 계획 단계의 수요를 체계적으로 놓친다.** 노이즈가 아니라 사각지대다.

더 중요한 이유는 **수요의 모양이 실제로 다르다**는 점이다. 코스형은 한 지점에 몰리는 것이 아니라 **여러 지점을 순차 방문**한다. 따라서 필요한 대응도 다르다.

| 유형 | 부하가 걸리는 곳 | 필요한 대응 |
| --- | --- | --- |
| 맛집형·예능 노출형 | 특정 점포 | 점포 앞 대기 관리, 주변 주차 |
| **코스·일정형** | **지점 간 동선과 이동 시간대** | 교차지점 분산, 시간대 분산 안내 |

이는 매뉴얼 p.13 **네트워크 보행 흐름형**의 관리 방안(교차지점 분산·일방통행·흐름 유지)과 직접 연결된다.

### 구현 위치
- `data/schema/_envelope.schema.json` → `content_type` enum
- `agents/prompts/agent2_content_type.md` → 유형 정의 및 판별 규칙 (v1.1)
- `agents/agent2_apply.py` → 해당 2건 재분류

## D-02. 데드존 신호는 `zone_signal` 필드로 별도 기록한다

### 결정
`content_type`은 그대로 두고, 항목에 **선택 필드 `zone_signal`**을 추가한다. 값은 `핫존` / `데드존` 둘뿐이며, 해당 없으면 필드를 넣지 않는다.

`관광무관`으로 분류된 영상도 `zone_signal`은 가질 수 있다. 집계에서 빠지는 것과 신호를 버리는 것은 다르다.

### 근거
오늘 2건이 지역 쇠퇴를 다뤘고 현재는 `관광무관`으로 버려지고 있다.

- 「바다의 금강산? 거제도 해금강 마을, 호텔도 횟집도 파리만 날린다」 16.4만 회
- 「관광객은 오는데 왜 빈 건물만 늘어났나… 거가대교가 바꾼 거제도의 몰락」 5.3만 회

**이 정보를 버리면 안 되는 이유가 두 가지 있다.**

첫째, 매뉴얼 **Tier1 KPI '핫존-데드존 균형도(지니계수)'**(p.15)가 정확히 이 격차를 측정한다. 정량 지표에 대한 정성 근거가 콘텐츠에서 나온다.

둘째, 그리고 더 중요하게 — **데드존은 분산 정책의 목적지다.** 혼잡 관리의 핵심은 사람을 줄이는 게 아니라 옮기는 것이다. 매뉴얼 p.47은 "방문객을 여러 공간으로 나누어 특정 지역 과밀 해소 / 주변 상권까지 소비 확산"을 상생방안으로 제시한다. 어디가 비어 있는지 모르면 어디로 보낼지 정할 수 없다.

즉 해금강 마을은 **문제가 아니라 해답의 후보**다.

`content_type`에 `쇠퇴형` 같은 값을 추가하지 않은 이유: 다른 모든 값이 "수요를 만드는 유형"인데 여기에 "수요가 빠지는 유형"을 섞으면 축이 무너진다. 비중 집계도 무의미해진다.

### 구현 위치
- `data/schema/content_type.schema.json` → `items[].zone_signal`, `data.zone_signals` 집계
- `agents/prompts/agent2_content_type.md` → 판정 지침 (v1.1)
- 활용: AREA 1 핫스팟 화면에서 "분산 후보지"로 표시 / AREA 3 브리핑의 분산 유도 조치 근거

## D-03. 에이전트③은 매칭 결과를 자르지 않고 `rank`를 매긴다

### 결정

**매칭 규칙 (순서대로 적용)**

| 단계 | 조건 | 불일치 시 |
| --- | --- | --- |
| 1차 | 항목의 `단계` 배열에 현재 `alert_level`이 포함 | 제외 |
| 2차 | 항목의 `공간유형`이 비어 있거나(전 유형 공통) 현재 지점 유형과 교집합 존재 | 제외 |
| 3차 | 항목의 `프로파일`이 비어 있거나 현재 `profile_tags`와 교집합 존재 | 제외 |
| 가중 | `content_type` 일치 시 정렬에서 우대 | **제외하지 않음** |

`content_type`은 필터가 아니라 정렬 가중치다. 콘텐츠 유형이 다르다고 해서 안전 조치를 빼면 안 되기 때문이다.

**정렬 (rank 부여 기준)**
1. 우선순위 — 최우선 > 높음 > 보통
2. 시점 — 오전(준비) → 운영 중(모니터링) → 비상 대응 → 마감(평가)
3. 콘텐츠 유형 일치 여부
4. id 오름차순

**개수 상한: JSON에는 두지 않는다.** 매칭된 항목을 전부 담고 `rank`만 부여한다. 화면 표시 개수(권장: 시점별 상위 5건 + 더보기)는 프론트가 결정한다.

### 근거
JSON은 계약이고 화면은 표현이다. **계약 단계에서 데이터를 자르면 되돌릴 수 없다.** 지금은 브리핑 화면에서 5건만 보여주더라도, 나중에 "전체 체크리스트 인쇄" 같은 화면이 생기면 잘린 데이터로는 만들 수 없다.

반대로 전부 담아두면 화면은 언제든 원하는 만큼 보여줄 수 있다. 자르는 쪽이 정보를 잃고, 담는 쪽은 잃지 않는다.

`content_type`을 필터가 아닌 가중치로 둔 이유는 안전 때문이다. "출입구 전면 통제"(매뉴얼 p.50, 5단계)는 콘텐츠 유형과 무관하게 필요한 조치다. 유형으로 거르면 이런 항목이 사라질 수 있다.

### 구현 위치
- `data/schema/checklist.schema.json` → `items[].rank`
- `agents/prompts/agent3_manual_match.md` (작성 예정)

## D-04. 브리핑은 3문단 400~600자, 구조를 고정한다

### 결정

**구조 (고정)**

| 문단 | 내용 | 필수 요소 |
| --- | --- | --- |
| 1 | 현재 상황 | 경보 단계, 3중 교차검증 결과, 판정 근거 |
| 2 | 예상되는 전개 | 예측 방문객, 피크 예상일, 예측 구간과 모델 성능 |
| 3 | 권고 조치 | 3건 이내, 각각 매뉴얼 쪽수 표기 |

**분량**: 400~600자. **톤**: 담당 공무원에게 보고하는 문어체.

**금지**
- 매뉴얼에 없는 조치 제안
- 출처 없는 수치
- "AI가 분석한 결과" 류의 자기 언급
- 단정적 예측 (예측은 항상 구간과 함께)

**필수**
- 모든 수치에 출처
- 모든 조치에 매뉴얼 쪽수
- 불확실한 부분은 불확실하다고 명시

### 근거
분량을 고정하는 이유는 **읽히기 위해서**다. 담당자가 아침에 확인하는 화면이라면 한 화면에 들어가야 한다. 600자를 넘으면 스크롤이 생기고, 스크롤이 생기면 마지막 문단(권고 조치)이 안 읽힌다. 가장 중요한 내용이 맨 뒤에 있으므로 분량 초과는 곧 기능 상실이다.

구조를 고정하는 이유는 **비교 가능성**이다. 매일 같은 순서로 나오면 어제와 달라진 부분이 눈에 띈다. 자유 형식이면 매번 읽어야 한다.

조치를 3건으로 제한한 이유: 매뉴얼 p.50 체크리스트도 시점별 4건 내외다. 한 번에 실행 가능한 수를 넘기면 우선순위가 사라진다.

### 구현 위치
- `agents/prompts/agent5_briefing.md` (작성 예정)
- AREA 3 화면

## D-05. 경보 상향 임계를 단계별로 차등한다

### 결정

| 전이 | 필요 조건 |
| --- | --- |
| 관심 → 주의 | 3개 신호 중 **1개** 임계 초과 |
| 주의 → 경계 | 3개 신호 중 **2개** 임계 초과 |
| 경계 → 심각 | 3개 신호 중 **3개** 초과 **또는** 혼잡도 단계 5 실측 |

**하향은 상향보다 보수적으로**: 2회 연속 관측에서 조건 미달일 때만 한 단계 내린다.

### 근거
단계마다 조치 비용이 다르므로 요구 확신도도 달라야 한다.

'주의'의 조치는 모니터링 강화와 안내다. 틀려도 비용이 작으므로 **민감하게** 잡는 것이 맞다. 조기경보 시스템에서 놓치는 비용은 잘못 울리는 비용보다 크다.

반면 '심각'의 조치는 매뉴얼 p.50 기준 **출입구 전면 통제**다. 관광객을 돌려보내고 상인 매출에 직접 영향을 준다. 이 단계에서 오경보는 시스템 신뢰를 잃게 만들고, 한 번 신뢰를 잃으면 다음 경보도 무시된다.

매뉴얼 p.20도 "경보 기준 설정: 혼잡 단계(4~5), 지속시간, 유입증가율, 정체 고착시간 기준값 정의"라 하여 단일 기준이 아닌 복합 기준을 제시한다.

하향을 보수적으로 한 이유는 **깜빡임 방지**다. 임계 근처에서 값이 오르내릴 때 경보가 매일 바뀌면 현장은 대응할 수 없다. 인력 배치는 하루 단위로 정해지기 때문이다.

### 구현 위치
- `data/schema/signal_status.schema.json` → `data.escalation` (현재 단계에서 다음 단계로 가는 조건과 충족 여부)
- 판정 로직 구현 시 이 규칙을 따른다

## D-06. 검색어 세트를 템플릿으로 고정한다

### 결정
기본 검색어를 다음 3개로 고정한다.

```
{지역} 여행
{지역} 가볼만한곳
{지역} 맛집
```

지역명 단독 검색(`거제`)은 **쓰지 않는다.** POI 단위 검색(`매미성`, `외도` 등)은 필요 시 `--queries`로 추가하되 기본 세트에는 넣지 않는다.

### 근거
**재현성**이 첫째 이유다. 시계열로 "콘텐츠가 늘고 있다"를 말하려면 수집 조건이 같아야 한다. 검색어가 매번 바뀌면 건수 변화가 실제 수요 변화인지 검색어 변화인지 구분할 수 없다. 조기경보 시스템에서 이건 치명적이다.

**지역명 단독 검색을 뺀 이유**는 오늘 실측으로 확인했다. `거제`로 검색하니 상위가 인물 예능 콘텐츠로 채워졌고, 관광 콘텐츠는 밀려났다. 지역명이 인물명·상품명과 겹치는 경우는 흔하므로(경주, 광주 등) 구조적 문제다.

**POI 검색을 기본에서 뺀 이유**는 쿼터다. 검색 1회가 100 units이고 하루 한도가 10,000이다. 3개 세트면 실행당 300 units로 하루 33회 실행할 수 있다. POI를 10개 추가하면 실행당 1,300 units가 되어 하루 7회로 줄어든다. POI 단위 정보는 이미 `poi_mentioned` 추출로 얻고 있으므로 중복 투자다.

### 구현 위치
- `collection/youtube_collect.py` → `--queries` 기본값

## D-07. 선행 신호로 고르는 조치와 현장 혼잡으로 고르는 조치를 분리한다

### 결정
두 가지 장치를 둔다.

**① 시점에 `사전(예보 대응)`을 추가한다.** 기존 4개 시점(오전·운영 중·비상·마감)은 매뉴얼 p.50의 **하루 일과**다. 며칠 앞서 준비하는 조치(p.20 시나리오 ①②, p.13 유형별 관리)를 담을 자리가 없었다.

```
사전(예보 대응) → 오전(준비) → 운영 중(모니터링) → 비상 대응 → 마감(평가)
```

**② 매칭에 혼잡도 단계 조건을 추가하되, 미달이면 버리지 않고 `대기`로 표시한다.**

| 조건 | 결과 |
| --- | --- |
| 경보 단계·공간 유형·프로파일 일치 + 혼잡도 조건 충족 | `status: 발동` |
| 경보 단계·공간 유형·프로파일 일치 + 혼잡도 조건 **미달** | `status: 대기` + `standby_condition` ("혼잡도 4단계 이상 관측 시") |
| 경보 단계·공간 유형·프로파일 불일치 | 제외 (`excluded_count`) |

rank는 `발동`을 먼저 매기고, 그 안에서 D-03 정렬을 따른다.

### 근거
매뉴얼 조치 대부분은 **현장에 사람이 이미 몰린 뒤**를 전제로 한다 — p.50 "4단계(높음) 감지 시", "비상 대응 5단계(위험) 발생 시". 반면 우리 경보는 콘텐츠·SNS·내비 검색이라는 **며칠~몇 주 앞의 선행 신호**에서 나온다.

D-03만으로는 이 차이를 구분하지 못한다. D-05에 따라 선행 신호 3개가 모두 임계를 넘으면 '심각'이 되고, 그러면 **현장 혼잡도가 3단계여도 "출입구 전면 통제"(p.50, 최우선)가 매칭된다.** 유튜브 조회수와 검색량만으로 관광객을 돌려보내라고 권고하는 셈이며, D-05가 막으려 한 바로 그 오경보다.

그렇다고 현장 조치를 제외하면 조기경보의 가치 하나를 잃는다. "혼잡도 4단계에 도달하면 즉시 할 일"을 **미리 알려주는 것** 자체가 준비 시간을 만든다. 그래서 버리지 않고 `대기`로 둔다. D-03의 원칙(계약 단계에서 자르지 않는다)과도 맞는다.

- `manual/README_태그체계.md`, `scripts/validate_manual.py` → 시점 값 추가

## D-08. 에이전트③에서 LLM은 판정만 하고, 조치 문장은 코드가 복사한다

### 결정

| 단계 | 누가 | 내용 |
| --- | --- | --- |
| 후보 선별 | **코드** | D-03 1~3차 필터 + D-07 혼잡도 조건 |
| 상황 판정 | **LLM** | 신호 조합을 보고 매뉴얼 p.39의 상황 유형 4종(유입 급증형·병목 정체형·안전 위험형·민원 급증형) 중 해당하는 것과 근거 |
| 범위 밖 이슈 | **LLM** | 신호에는 있으나 매뉴얼이 다루지 않는 문제 (예: 바가지 요금) — 조치를 만들지 않고 표시만 |
| 항목별 관련도 | **LLM** | 후보 각각에 `핵심`/`관련`/`일반` + 한 문장 사유 |
| 정렬·rank | **코드** | D-07 → D-03 (관련도는 D-03의 3순위 키 자리에 들어간다) |
| 조치 문장·쪽수·원문 | **코드** | 구조화된 매뉴얼 레코드에서 그대로 복사 |

LLM 출력은 JSON 스키마로 강제하고, 항목 id는 **후보 id의 enum**으로 제한한다. LLM이 존재하지 않는 항목을 만들거나 후보를 빠뜨리면 검증에서 실패한다.

LLM 호출부는 백엔드를 교체할 수 있게 만든다: Anthropic API / **Upstage Solar API** / OpenAI 호환 로컬 서버(vLLM·Ollama) / 저장된 응답 재생.

**운영 모델은 Upstage `solar-pro3`로 정한다 (09.13).** 무료로 계속 돌릴 수 있는 모델이다. 성능이 모자라면 모델을 바꾸기 전에 프롬프트·추론 강도·코드 보정으로 먼저 푼다.

### 근거
**"AI가 정책을 창작하지 않는다"를 구조로 보장하기 위해서다.** LLM이 조치 문장을 출력하게 하면, 아무리 프롬프트로 금지해도 요약·윤문이 섞일 수 있다. 매뉴얼은 공공누리 4유형(변경금지)이라 이것은 신뢰성 문제이자 이용조건 문제다. LLM에게 id와 판정만 받고 문장은 코드가 복사하면, **LLM이 무엇을 출력하든 화면의 조치 문장은 매뉴얼 원문이다.**

**LLM에게 거르는 권한을 주지 않는 이유는 안전이다.** 관련도가 낮다고 판정된 항목도 목록에 남는다(D-03). LLM이 "이 상황엔 필요 없다"고 판단해 안전 조치가 사라지는 경로를 막는다.

그러면 LLM은 왜 필요한가. 규칙 표로 풀 수 없는 부분이 두 가지 있다.
- **상황 판정**: "예능 노출형 63% + 특정 점포 5곳 반복 언급 + 바가지 논란 1건 + 데드존 1곳"이 어떤 혼잡 상황을 만들지는 조합의 문제다. 콘텐츠 유형 하나로 상황 유형이 정해지지 않는다.
- **범위 밖 식별**: 바가지 논란은 과열 신호지만 혼잡도 매뉴얼에는 대응 조치가 없다. 이를 알아채고 **조치를 지어내는 대신 "매뉴얼 범위 밖"으로 표시**하는 것은 규칙으로 만들기 어렵다.

로컬 LLM도 지원하는 이유: 시연 환경의 네트워크·비용 제약에 대비하고, 지자체 내부망 배포(외부 API 반출 불가) 시나리오를 서식4에서 확산 가능성 근거로 쓸 수 있다. 판정 범위를 좁혀 둔 설계 덕분에 소형 모델로도 동작할 여지가 크다.

### 구현 위치
- `agents/prompts/agent3_manual_match.md` → 시스템 프롬프트 (코드가 이 파일에서 읽는다)
- `agents/llm_client.py` → 백엔드 3종
- `agents/agent3_match.py` → 필터·LLM 호출·검증·정렬·출력
- `data/schema/checklist.schema.json` → `items[].relevance`, `data.assessment`

## D-10. 브리핑의 수치는 facts 목록에서만 쓰고, 코드가 대조 검증한다

### 결정
에이전트⑤는 수치를 직접 읽거나 계산하지 않는다.

1. 코드가 입력 JSON에서 **사람이 읽는 표기로** 수치 목록(facts)을 만든다. 예: `0.42` → `42% (임계 30%, 초과)`, 예측값은 항상 80% 구간과 한 묶음
2. LLM은 문장을 쓰고, 인용한 fact id를 `used_facts`에 밝힌다
3. 코드가 LLM이 쓴 문장의 **모든 숫자**가 `used_facts`의 값 안에 있는지 검사한다. 하나라도 없으면 반려하고, 이유를 붙여 1회 재작성시킨다
4. 권고 조치 문장과 쪽수는 D-08처럼 코드가 원문을 넣는다. 3문단은 `도입 문장 + ① 원문 (p.쪽) — 사유` 틀로 조립한다
5. 같은 방식으로 분량(400~600자), 자기 언급·단정 표현, "예측값에는 구간"을 검사한다

출력 `briefing.json`에는 인용된 facts와 출처가 함께 들어가 화면에서 수치마다 출처를 붙일 수 있다.

### 근거
D-04의 "출처 없는 수치 금지"를 **프롬프트 부탁에서 검증 가능한 규칙으로** 바꾸기 위해서다. 브리핑은 자연어라 LLM이 비율을 환산하거나 반올림한 숫자, 두 값을 더한 숫자를 쓰기 쉽다. 이런 숫자는 그럴듯해서 사람이 검토해도 놓친다. 표기를 코드가 미리 정해 두면 LLM이 계산할 이유가 없어지고, 검사도 문자열 대조로 끝난다.

검사가 막지 못하는 것도 있다. facts에 있는 숫자를 **다른 맥락에 붙이는 것**(예: 17%를 SNS 언급량이라고 쓰는 것)은 숫자 대조로 걸리지 않는다. 그래서 facts의 label을 문장에 가깝게 쓰고, 이 한계는 서식4에 명시한다.

### 보완 (09.13) — facts는 필요한 만큼만 준다
solar-pro3로 실제 실행해 보니 모델은 **받은 facts를 전부 나열하려 했다.** 피크 예상일 3개를 구간과 함께 주자 "1개만 쓰라"는 지시를 무시하고 3개를 모두 써서 2문단이 258~288자가 됐다. JSON 스키마의 `maxLength`도 무시됐다(40자 제한에 99자 출력). 반려 사유를 알려 줘도 1·2문단은 같은 길이로 반복됐다.

입력을 줄이자 2문단은 177자로 줄었지만 1문단이 233~251자로 길어졌고, 넘친 문장만 떼어 "N자 이하로 줄여라"라고 요청해도 251자를 233자로만 줄였다. → D-11로 이어진다.

## D-11. 브리핑 1·2문단은 코드가 데이터로 쓰고, LLM은 3문단의 판단만 맡는다

### 결정

| 부분 | 누가 |
| --- | --- |
| 1문단 현재 상황 | **코드 템플릿** — 경보 단계 변화, 넘은 신호·못 넘은 신호(값·임계), 실수요 판정, 다음 단계 조건 |
| 2문단 예상 전개 | **코드 템플릿** — 최대 피크일(구간 포함), 그 밖의 피크일, 모델 성능, 예상 혼잡 유형(에이전트③) |
| 3문단 종합 판단 한 문장 | LLM |
| 3문단 권고 조치 선택(1~3건, 우선순위 순)과 사유 | LLM |
| 3문단 조치 원문·쪽수 | 코드 (D-08) |
| 3문단 범위 밖 문장 | 코드 템플릿 (에이전트③의 `out_of_scope`) |
| 분량 맞추기 | 코드 — 600자를 넘으면 LLM이 고른 순서의 뒤에서부터 조치를 뺀다(최소 1건) |

실수요 판정 문장은 v3 회의안 A의 규칙을 그대로 코드로 옮겼다: 세 신호 모두 초과 → 실수요, 관심만 초과 → 실수요 미확정, 관심·의도 초과 → 방문 전환 가능성 높음.

### 근거
1. **v3 원칙과 맞다.** "규칙으로 되는 것을 LLM으로 처리하지 않는다." 1·2문단은 구조가 고정된 데이터를 문장으로 옮기는 일이라 규칙으로 충분하다.
2. **D-04의 비교 가능성이 강해진다.** 매일 같은 문장 틀이면 담당자가 어제와 달라진 숫자만 보면 된다.
3. **D-10의 한계가 1·2문단에서 사라진다.** 숫자를 코드가 데이터에서 직접 넣으므로 "맞는 숫자를 틀린 맥락에 붙이는" 오류가 구조적으로 불가능하다. LLM이 쓰는 부분(종합 판단·사유)만 숫자 대조 검사를 받는다.
4. **실측 근거.** solar-pro3는 분량 제한을 지키지 못했다(D-10 보완 참고). 모델을 바꾸지 않고(solar-pro3 고정) 문제를 푸는 방법이다.

**LLM의 역할이 줄었는가?** 줄었다. 하지만 남은 일 — 신호 조합을 보고 **어떤 조치를 먼저 권할지, 왜 지금인지** — 가 브리핑에서 판단이 필요한 유일한 부분이다. 서식4에는 "LLM은 판단이 필요한 곳에만 쓰고, 수치 문장은 코드가 데이터에서 생성한다"로 쓴다.

- `agents/agent5_briefing.py` → `render_situation`, `render_outlook`, `render_out_of_scope`, `fit_actions`
- `agents/prompts/agent5_briefing.md` v2.0

### 구현 위치

- `scripts/validate_data.py` → `check_briefing` (문단 순서, 글자 수, 조치 원문·쪽수 포함 여부)

## D-12. 에이전트① 타임라인: 근거는 원문 대조, 신호는 전국 분포 임계 (09.16)

### 결정

**1. 역할 분담**

| 부분 | 누가 |
| --- | --- |
| 기사에서 사건·날짜·원문 인용 찾기 | LLM 세션(웹 검색) → `agents/evidence/agent1_timeline_evidence.json` |
| 인용문이 원문에 글자 그대로 있는지, 보도일이 페이지에 있는지 | 코드 (`--verify-sources`) |
| 기사 수치 | 코드 — `value_text`가 인용문에 그대로 있고 숫자로 풀었을 때 `value`와 같아야 함 |
| 영상 날짜·조회수 | 코드 — DB `youtube_video`에서만 읽음 (손으로 쓰지 않음) |
| 시스템 신호(검색 급증) | 코드 — 아래 규칙 |
| 시차(`lags`)·리드타임 | 코드 |

**2. 시스템 신호 규칙 (임시 — 역할2 백테스트로 교체 가능)**

- 지표: 네이버 검색지수 일별
- 통계량: 그날 값 ÷ 364일 전(같은 요일) 값의 **최근 7일 중앙값**
- 임계: **2024년 전국 228개 지역(합성 제외) 전 일자의 99백분위** = 1.73배. 사례 지역을 보고 정하지 않는다
- 확정: 임계 초과가 **7일 연속**이면 7번째 날에 신호. 외지인 방문자수(99백분위 1.51배)는 같은 방식으로 계산해 `signal_check`에만 남긴다

**3. 조치의 인정 기준**: `is_case_response=true`는 방문 수요 증가나 사례 논란에 대응한 수용·안전·질서·가격 관리 조치만. 홍보·마케팅, 매년 하는 정례 행사는 false. `lags.first_action_date`는 `actor=행정`이면서 인정된 첫 조치다.

**4. 사례 성격 3종**: 수요 급증 / 평판 위기 / 비관광 급증. 신호가 없었던 것도 `signal_check`에 남긴다.

**5. 파일**: 기본 지역(거제)은 `timeline.json`, 그 밖의 사례는 `timeline_{시군구코드}.json`. `validate_data.py`가 둘 다 검사한다.

### 근거

1. **"AI가 근거를 지어내지 않는다"를 검사로 만든다.** 웹 요약 도구가 돌려준 인용은 원문과 다를 수 있다 — 실제로 여수시 첫 대응일이 요약에서는 7/16, 원문에서는 7/4였다. 원문 대조가 없으면 이런 차이가 화면까지 간다. 변조 테스트(인용 한 단어, 보도일 하루, 수치, 영상 ID, 지역, 기점 누락)를 모두 잡는 것을 확인했다.
2. **평균이 아니라 중앙값, 1일이 아니라 7일 지속**: 인제 산불(2025-04-26) 당일 검색이 전년의 35배였지만 3일 만에 꺼졌다. 사례 6개 지역의 설·추석 방문자 급증도 4~6일이라 걸러졌다. 다만 **전국으로 넓히면 2025년 긴 연휴(설 1월 말, 추석 10월 초)는 일부 지역에서 7일을 넘었다** — 아래 한계 참고. 확정일을 첫날이 아니라 7번째 날로 둔 것은 **미래를 보지 않기 위해서**다.
3. **전국 분포로 임계를 정한다.** 사례 지역을 보고 임계를 고르면 적중률이 부풀려진다. 99백분위는 "전국 모든 지역·날짜 중 상위 1%"라 설명이 쉽다.
4. **정례 행사를 대응으로 세면 시차가 조작된다.** 거제 6.12 바가지요금 캠페인은 2025년 5월에도 한 개장 전 행사다. 이것을 첫 대응으로 쓰면 "확산 후 3주 만에 대응"이라는 사실이 아닌 서술이 된다(09.12 문서의 서술을 정정한 이유).

### 알려진 한계

- **검색 지표 단독 신호는 대부분 재난·사건에서 울린다.** 전국 검색 신호 47건(29개 지역, 2025-01~2026-08, `data/handoff/signal_episodes.csv`) 중 최고치 상위 12건을 확인하니 관광 수요는 **영월 1건**이었다. 나머지는 2025-03 영남 산불(의성·산청·안동·울주·청송·영양·영덕 7건), 2025-04 광명 신안산선 붕괴, 2026-04~06 부산 북구 보궐선거, 2025-01 무안(제주항공 참사 직후로 추정), 2026-08 거제 폭우다. **검색 신호는 '무엇 때문에 뜨는가'를 판별하는 단계(에이전트② 콘텐츠 유형, 뉴스 문맥) 없이는 경보로 쓸 수 없다** — 계량성과 핵심 ②(오경보율)에 직접 반영해야 한다
- **외지인 방문자 신호도 명절에 울린다.** 전국 23건 중 20건이 2025-01(설)·2025-10(추석) 시작이다. 전년 동요일 비교로는 음력 명절 이동을 지울 수 없으므로, 명절 기간을 달력으로 제외하는 보정이 필요하다
- **평판 위기는 탐지하지 못한다.** 여수·울릉·속초 모두 검색·방문자 신호가 없었다. 수요를 만들지 않기 때문이며, 이 시스템의 범위 밖이라고 서술한다
- **시군구 방문자수로는 지점 급증이 보이지 않는다.** 거제·영월 모두 외지인 방문자수는 임계를 넘지 않았고, 급증은 해수욕장·청령포 집계에서만 확인됐다
- 기사 조사는 전수가 아니다. 보도되지 않은 더 이른 조치가 있을 수 있다

## D-13. signal_status 실데이터 판정: 월별 초과분·일별 지속 신호, 혼잡도는 지어내지 않는다 (09.16)

### 결정

**1. 3중 교차검증 신호 (v3 회의안 A의 구성 유지)**

| 단계 | 지표 | 통계량 | 임계 |
| --- | --- | --- | --- |
| 관심 | SNS 언급량 (데이터랩 월별 패널) | 전월 대비 증가율 − 같은 달 전국 중앙값 (%p) | 전국 90백분위 = +17.1%p |
| 의도 | 내비게이션 검색건수 (같은 패널) | 같은 방식 | 전국 90백분위 = +26.5%p |
| 실현 | 외지인 방문자수 (일별, data.go.kr) | 전년 동요일 대비 배율 7일 중앙값이 7일간 유지된 수준의 월중 최고치 | 1.51배 (D-12와 같은 규칙) |

**2. 경보 단계**는 D-05를 첫 달(2025-09)부터 차례로 적용하고 `history`에 남긴다. 상향은 한 달에 한 단계, 하향은 현 단계 요건 미달이 2개월 연속일 때 한 단계.

**3. 값이 없으면 지어내지 않는다.**
- `congestion_level`을 필수에서 뺐다. 실측이 없으면 생략한다. 이때 에이전트③은 **조건 없는(1~5단계 전체) 조치만 발동**하고 혼잡도 조건이 붙은 현장 조치는 모두 대기로 둔다
- 신호 원천 값이 비면 `value: null` + `missing_reason`, `exceeded: false`. 0으로 채우지 않는다

**4. 파일**: 거제는 `signal_status.json`, 사례 지역 5곳은 `signal_status_{코드}.json`. 에이전트③⑤는 기본 파일(거제)만 읽는다.

### 근거

1. **전년 대비를 쓸 수 없다.** 월별 패널이 2025-08~2026-07 12개월뿐이다. 전월 대비를 그대로 쓰면 명절·계절 변동이 신호가 된다 — 2025-10 내비 검색 전국 중앙값이 추석으로 +87%였다. 전국 중앙값을 빼면 전국이 같이 움직이는 몫이 지워진다.
2. **실현 신호를 패널에서 가져오지 않은 이유**: 패널의 `visitors_yoy_pct`는 3,108행 중 539행에만 값이 있다(영월은 전부 비어 있음). 일별 외지인 방문자수는 228개 지역 전체가 있고, D-12와 같은 규칙(7일 지속)으로 짧은 명절 이동은 걸러진다(긴 연휴는 일부 지역에서 남는다 — D-12 한계).
3. **표시값과 판정이 어긋나지 않게**: 처음에는 월중 7일 중앙값 최고치를 값으로 썼더니 인제 7월이 "1.7배, 임계 1.51배, 미달"로 나왔다(7일 지속 미충족). 값을 "7일간 유지된 수준"으로 바꾸면 값 ≥ 임계와 초과 판정이 정확히 같아진다.
4. **90백분위(주의는 민감하게, D-05)**: 월 단위라 지역당 판정 기회가 1년에 11번이다. 99백분위면 기대 초과가 지역당 연 0.1회 수준이라 주의 단계의 민감도와 맞지 않는다.
5. **혼잡도 3을 넣지 않은 이유**: 목업의 3은 손으로 넣은 값이다. 실데이터 파일에 그대로 두면 에이전트③이 "혼잡도 3단계 관측"을 근거로 운영 중 모니터링 조치 3건을 발동한다. 없는 관측을 근거로 조치가 나가는 것은 D-07이 막으려던 것과 같은 문제다.

### 알려진 한계

- **관광지의 명절·계절 효과는 전국 평균보다 커서 남는다.** 10월(추석)에 거제·영월·여수·인제가 주의로 올랐고, 인제는 5월부터 경계에 머물렀다. 전년 대비가 가능해지면(패널 기간 확장) 교체한다
- **표본 내 임계**: 과거 월 판정에도 2026-07까지의 분포로 정한 임계를 썼다. 백테스트 성과로 쓰려면 역할2가 시점별 임계로 다시 계산해야 한다
- **월 단위 사후 판정**: 최신 월이 2026-07이라 조회일보다 7주 늦다. 실시간 조기경보 주장은 D-12의 일별 검색 신호로 한다
- 에이전트③의 공간 유형·핫스팟, 에이전트⑤의 예측 문단은 여전히 목업 입력이다(`_mock: true`)

### D-13 개정 (09.20) — 전월 대비 → 전년 동월 대비

데이터 담당이 09.17·09.19에 월별 패널을 **2020-01~2026-08(80개월)**로 확장했다. 전년 대비를 쓸 수 없어 전월 대비를 썼던 제약이 사라져 다음을 바꿨다.

### D-14 (09.24) — 데이터랩 월간을 예측 모델 입력으로 허용, 근거 기사는 금지 확정

### D-17 (09.26) — 지역 승률은 sMAPE가 잡음보다 클 때만 인용한다

팀원이 "검색 승률 44.3%면 오히려 나빠진 것 아니냐"고 물어 재측정했다. 씨앗 묶음 3벌
((0,1,2)/(3,4,5)/(6,7,8))로 같은 실험을 돌린 결과다.

| 비교 | 씨앗 묶음별 승률 | 흔들림 폭 | sMAPE 차이 범위 |
| --- | --- | --- | --- |
| 달력 추가 | 94.3 / 95.2 / 94.3% | 0.9%p | −1.382 ~ −1.363 |
| 데이터랩 월간 추가 | 75.4 / 77.2 / 75.0% | 2.2%p | −0.316 ~ −0.273 |
| 네이버 검색 추가 | 44.3 / 54.4 / 51.3% | **10.1%p** | +0.020 ~ +0.026 |

**효과가 실재하는 변수의 승률은 거의 고정이고, 효과가 없는 변수의 승률만 크게 흔들린다.**
신호가 없으면 어느 지역이 좋아지는지가 사실상 무작위로 정해지기 때문이다.

| 항목 | 결정 |
| --- | --- |
| 승률 인용 조건 | 그 변수의 **sMAPE 차이가 씨앗 잡음보다 클 때만** 승률을 숫자로 쓴다 |
| 달력·데이터랩 승률 | 그대로 인용 가능 (각각 ±0.9%p, ±2.2%p) |
| 검색 승률 | **인용 금지.** "차이 없음"으로만 서술한다 |
| 반영 | `freeze.py`의 금지 문장 목록과 `확정수치_0924.md`에 안정성 표를 넣었다 |

09.22에 세운 규칙("씨앗 잡음보다 작은 차이는 개선이라 부르지 않는다")을 sMAPE에만 적용하고
승률에는 적용하지 않은 것이 원인이다.

### D-18 (09.26) — 검색 변수에서 절대 수준을 뺀다

검색지수는 관광 수요와 무관하게 해마다 내려간다(전국 평균 1~8월 기준 67.2 → 47.8,
228곳 중 217곳 하락, 중앙값 0.73배). 같은 기간 방문자는 1.05배로 늘었다.
지역 간 수준 차이도 110배(2.22~244.54)다.

그런데 `naver_last`·`naver_mean7`·`naver_mean28`이라는 절대 수준을 전국 공통 모델에
넣고 있었다. 누출은 아니지만 (a) 수준이 지역 이름표 역할을 하고 (b) 학습 구간 기준이
시험 구간에서 27% 어긋나는 분포 이동에 노출된다.

| 항목 | 결정 |
| --- | --- |
| 검색 변수 | 전부 **'그 지역 직전 1년 평균 대비'** 비율로 바꾼다 |
| 전년 대비 | **같은 날 전국 중앙값으로 나눠** 공통 하락분을 제거한다 |
| 구현 | `analysis/src/forecast/naver_redesign.py` |
| 결과 | 씨앗 묶음 3벌 모두에서 구버전보다 낮음(9.222~9.242 vs 9.246~9.252). 다만 기준(검색 없음) 대비는 여전히 차이 없음 → **결론 불변** |

이 원칙은 앞으로 추가되는 외부 지표 전반에 적용한다. **전국 공통 모델에 절대 수준을 넣기 전에
그 지표가 시간에 따라 표류하는지 먼저 확인한다.**
