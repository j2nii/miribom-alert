## 1. 한 장 요약

### 무엇을 물었나

우리 프로젝트의 원래 전제는 **"콘텐츠가 뜨면 검색이 먼저 늘고, 그다음 사람이 몰린다. 그러니 검색을 보면 미리 알 수 있다"**였습니다.

저는 이것을 데이터로 확인하는 역할을 맡았고, 세 가지를 물었습니다.

1. 방문자 수를 **얼마나 잘 예측**할 수 있는가
2. **검색이나 추가 데이터**를 넣으면 실제로 좋아지는가
3. **급증을 미리** 알 수 있는가

### 무엇을 알아냈나

| 질문 | 답 | 근거 수치 |
| --- | --- | --- |
| 예측이 되는가 | **된다** | 7일 앞 예측 오차 12.27% → **8.98%** (26.8% 감축), 228개 시군구 전체 |
| 데이터랩 월간 지표가 도움이 되는가 | **도움 된다** | 오차 −0.273%p, 228곳 중 **75.4%에서 개선** |
| 네이버 검색이 도움이 되는가 | **안 된다** | +0.026%p (사실상 0), 여러 방식으로 재확인 |
| 급증을 미리 알 수 있는가 | **안 된다** | 2025년엔 잘 맞던 신호가 2026년엔 **방향이 뒤집힘** (AUC 0.94 → 0.22) |
| 그럼 쏠림은 어디에 있는가 | **지점(관광지)에 있다** | 지점 급증 108건 중 **106건(98%)이 시군구 총량에서 안 보임** |
| 왜 총량에서는 안 보이는가 | **원리적으로 못 본다** | 지점 급증이 총량에 남기는 흔적 0.38%p vs 총량 자체 흔들림 ±6.1%p → **1/16** |

### 그래서 프로젝트가 어떻게 바뀌었나

**"검색으로 미리 안다" → "총량으로는 안 보이니 지점을 봐야 한다"**로 주장의 축이 바뀌었습니다.

이게 나쁜 소식처럼 들릴 수 있는데, 오히려 **더 강한 카드**입니다. 이유는 [9장](#9-자주-나올-질문과-답)에서 자세히 설명합니다. 짧게 말하면, 이 대회는 데이터랩 활용 대회이고 우리는 **"데이터랩 지표가 실제로 얼마나 쓸모 있는지 정량 평가한 팀"**이 될 수 있기 때문입니다.

## 2. 배경 — 왜 이런 검증이 필요했나

### 2-1. 이 대회가 무엇을 보는가

공모요강 기준 1차 서면심사 100점의 배점입니다.

| 심사 항목 | 배점 | 우리가 여기에 내놓는 것 |
| --- | --- | --- |
| 창의성 및 혁신성 | 20 | 감시 단위 전환이라는 발상 |
| **데이터 활용도** | **30** | 공개 시점 규칙 준수, 지표별 기여도 정량 측정 |
| **효과성 및 성과 창출도** | **30** | 백테스트 수치 (예측 26.8% 개선, 사각지대 106건) |
| 사회적·경제적 파급력 | 20 | 전국 적용 가능, 신규 데이터 수집 불필요 |

역대 대상작은 **실제로 실행해서 낸 성과**였습니다(2024년 강진군: 방문객 43만 명 증가, 반값여행 소비 69억 원). 우리는 운영 실적이 없습니다. 그래서 **분석의 엄밀함**이 유일한 경쟁력입니다.

### 2-2. 엄밀함이 왜 그렇게 중요한가

분석에서 숫자를 좋게 만드는 건 사실 쉽습니다. 실수로 미래 정보를 쓰거나, 비교 대상을 잘못 잡으면 성적이 확 좋아집니다. 그런 숫자는 심사에서 한 번 찔리면 무너집니다.

그래서 저는 **"좋은 숫자"보다 "무너지지 않는 숫자"**를 목표로 잡았습니다. 실제로 그 과정에서 **우리 팀이 이미 공유했던 주장 두 개를 제가 직접 철회**했습니다([4-5절](#4-5-철회한-주장-2개--무엇이-틀렸고-어떻게-잡았나)). 아프지만, 심사 전에 발견한 게 다행입니다.

### 4-1. 방문자 수 예측 — 오차를 26.8% 줄였다

**질문**: 일주일 뒤 이 지역에 외지인이 몇 명 올지 맞힐 수 있는가?

**어떻게 쟀나**
- 228개 시군구 × 1,322일 = **301,416건**의 표를 만들었습니다(이걸 '패널'이라고 부릅니다)
- 2023~2024년 데이터로 배우고, 2025년으로 조정하고, **2026년 1~8월로 시험**했습니다
- 시험 구간의 정답은 모델에게 절대 보여주지 않았습니다

**숫자**

| 어떤 정보를 썼나 | 예측 오차(sMAPE) | 설명 |
| --- | --- | --- |
| 작년 같은 요일 값 그대로 | 12.27% | 아무것도 안 하고 작년을 베낀 수준 |
| + 달력(요일·공휴일·연휴 길이) | **9.23%** | 여기서 대부분이 좋아짐 |
| + 축제 | 9.23% | 거의 변화 없음 |
| + 네이버 검색 | 9.25% | **오히려 미세하게 나빠짐** |
| + 데이터랩 월간 지표 | **8.98%** | 확실한 개선 |

**무슨 뜻인가**
- 방문자 수 변동의 대부분은 **달력**이 만듭니다. 주말인가, 연휴인가가 압도적입니다
- "오차 26.8% 감축"은 12.27% → 8.98%를 말합니다
- sMAPE는 "평균적으로 몇 % 틀리는가"입니다. 8.98%면 1만 명 예측에 900명 정도 틀린다는 뜻입니다

**어디에 쓰나**: 서식4 계량성과 ①, 3)(1)

**더 볼 곳**: [`분석_결과_예측사다리.md`](분석_결과_예측사다리.md)

### 4-2. 추가 데이터 검증 — 데이터랩은 도움이 되고, 검색은 아니다

**질문**: 데이터를 더 넣으면 정말 좋아지는가? (팀에서 수집한 모든 데이터를 하나씩 시험)

**어떻게 쟀나 — 이게 이번 작업에서 가장 공들인 부분입니다**

"넣었더니 0.03%p 좋아졌다"는 말은 그 자체로는 의미가 없습니다. 같은 설정으로 다시 돌려도 그 정도는 그냥 흔들리기 때문입니다. 그래서 **관문 4개**를 만들었습니다.

| 관문 | 무엇을 막는가 | 쉬운 설명 |
| --- | --- | --- |
| ① 잡음 바닥 측정 | 우연을 개선이라 부르는 것 | 같은 실험을 3번 돌려서 "그냥 돌려도 이만큼은 흔들린다"를 먼저 잽니다 |
| ② 전진·후진 양방향 | 순서를 바꾸면 사라지는 개선 | "더했더니 좋아졌다"와 "빼면 나빠진다"가 **둘 다** 성립해야 인정 |
| ③ 신뢰구간·지역 승률 | 큰 지역 몇 곳이 만든 착시 | 228개 지역 중 몇 곳에서 좋아졌는지 셉니다 |
| ④ **위약 대조군** | 변수를 더 넣은 것 자체의 효과 | **지역 이름표를 뒤섞은 가짜 데이터**를 넣어 봅니다 |

④번에서 중요한 게 나왔습니다. **가짜 데이터만 넣어도 0.113%p 좋아졌습니다.** 변수를 18개 더 넣으면 모델이 조금 더 유연해지기 때문입니다. 이 대조군이 없었으면 개선폭을 **1.7배 부풀려** 보고할 뻔했습니다.

**숫자**

| 넣은 데이터 | 오차 변화 | 95% 신뢰구간 | 지역 승률 | 판정 |
| --- | --- | --- | --- | --- |
| 달력 | **−1.382%p** | [−1.513, −1.261] | 94.3% | 압도적 |
| 축제 | −0.020%p | [−0.042, −0.002] | 49.1% | 잡음 수준 |
| **네이버 검색** | **+0.026%p** | [−0.011, +0.065] | 44.3% | **효과 없음** |
| **데이터랩 월간** | **−0.273%p** | [−0.357, −0.199] | 75.4% | **효과 있음** |
| 데이터랩 − 위약 | −0.160%p | [−0.247, −0.089] | 61.8% | **순수 기여** |
| 과거 날씨 | −0.057%p | [−0.075, −0.040] | 66.7% | 잡음 수준 |

신뢰구간이 0을 포함하면(예: 검색의 [−0.011, +0.065]) **"차이 있다고 말할 수 없다"**는 뜻입니다.

**정직하게 덧붙일 것 하나**: 데이터랩의 이득은 대부분 **'방문자 수 월 집계'**에서 나옵니다. SNS 언급량·내비 검색·소비액만 남기면 개선이 잡음 수준으로 줄어듭니다. 그래서 "관심 지표가 도움이 된다"가 아니라 **"두 달 전 방문 규모를 알려주면 예측이 좋아진다"**가 정확한 서술입니다.

**쓰지 않기로 한 데이터**

### 4-3. 전국 지점 분석 — 총량은 쏠림의 98%를 못 본다 ★ 우리 주장의 본체

**질문**: 시군구 총량에 급증이 없다면, 쏠림은 도대체 어디에 있는가?

**어떻게 쟀나**
- 전국 관광지점 월별 입장객(데이터랩 인기 관광지 현황)을 썼습니다
- 2026년 3~6월, **1,048개 지점 × 139개 시군구**(관측 2,705건)
- 같은 지점의 같은 달을 전년과 짝지어 비교했습니다(표본이 바뀌는 걸 막기 위해)
- 시군구 총량에도 **똑같은 잣대**를 적용했습니다

**숫자**

| 단위 | 중앙값 | 상위 1% | 최대 |
| --- | --- | --- | --- |
| 관광지점 입장객 | 0.98배 | **3.14배** | **13.48배** |
| 시군구 총 방문자 | 1.01배 | 1.22배 | **1.31배** |

**시군구 총량은 어느 달에도 1.31배를 넘지 않습니다.** 총량만 보면 2026년 상반기에는 아무 일도 없었습니다.

| 확인 | 결과 |
| --- | --- |
| 지점 급증(2배 이상) | 108건 |
| 그중 같은 달 시군구가 평탄(1.2배 미만) | **106건 (98%)** |
| 해당 시군구 | **41개** — 전부 총량 기준 '이상 없음' |

**여기서 한 걸음 더 나갔습니다 — "당연한 산수 아니냐"에 대한 답**

심사에서 나올 가장 강한 반론은 이겁니다. *"관광지 하나는 시군구의 일부인데, 총량이 안 움직이는 건 당연하잖아요?"*

맞습니다. 그래서 **그 '당연함'의 크기를 쟀습니다.**

| 측정 | 값 |
| --- | --- |
| 지점 입장객이 시군구 월 방문자에서 차지하는 비중 | 중앙값 **0.38%** |
| 급증 106건이 총량에 실제로 더한 몫 | 중앙값 **+0.38%p** |
| 시군구 총량이 평소에도 흔들리는 폭 | **±6.1%p** |
| 신호 대비 잡음 | **16배** |
| 총량을 1.2배로 만들려면 그 지점 혼자 | **54배** |

**결론이 이렇게 바뀝니다**: 총량 감시는 쏠림을 *놓친* 게 아니라 **원리적으로 감지할 수 없습니다.** 더 좋은 모델이나 더 낮은 기준으로 해결되는 문제가 아니라, **지표 자체가 그 사건을 담지 못합니다.**

**사례로 보면**: 영월 청령포가 2026년 3월에 **11.9배**(7,106 → 84,251명)가 됐는데, 같은 달 영월군 총량은 **1.28배**였습니다.

**어디에 쓰나**: 서식4 핵심성과, 1) 문제점, 3)(2), 계량성과 ③

**더 볼 곳**: [`분석_지점쏠림_반론검증_0924.md`](분석_지점쏠림_반론검증_0924.md) (반론 8가지와 답 전부)

### 4-4. 조기경보 — 미리 맞히는 것은 실패했다 (정직하게 적는다)

**질문**: 다음 달에 어느 지역·지점이 뜰지 미리 알 수 있는가?

**어떻게 쟀나**
- 지역 × 월 단위로, 그 달 시작 시점에 손에 있는 정보만 써서 예측했습니다
- 검색, 데이터랩 SNS 언급량·내비 검색·숙박 검색·소비액, 그리고 이들을 합친 모델까지 시험

**숫자**

| | 2025-01 (검증) | 2025-10 (검증) | **2026-02 (시험)** |
| --- | --- | --- | --- |
| 결합 모델 판별력(AUC) | 0.860 | 0.941 | **0.217** |

AUC는 0.5가 동전 던지기입니다. 1에 가까울수록 잘 맞히는 것이고, **0.5보다 낮으면 반대로 맞히는 것**입니다.

**무슨 뜻인가**: 2025년에 0.86~0.94로 아주 좋아 보이던 모델이 2026년에 **0.217로 방향이 뒤집혔습니다.** 해마다 방향이 바뀌는 신호는 운영에 쓸 수 없습니다.

지점 단위로도 확인했습니다. 시군구 검색으로 "이 달에 이 지역 어느 지점이 뜰까"를 가려내는 판별력은 **AUC 0.482** — 판별력 없음.

**이 실패가 오히려 결론을 선명하게 만듭니다**

우리 제언이 **"검색을 보세요"가 아니라 "지점 입장객 자체를 감시 지표로 올리세요"**가 됩니다. 그리고 데이터랩이 이미 인기 관광지 월별 입장객을 제공하므로, **새로 수집할 데이터가 없습니다.** 활용 방식만 바꾸면 됩니다.

**어디에 쓰나**: 서식4 3)(5), 4) 한계

### 4-5. 철회한 주장 2개 — 무엇이 틀렸고 어떻게 잡았나

분석하면서 제가 팀에 공유했던 주장 두 개를 직접 취소했습니다. **이 과정 자체가 서식4의 신뢰도 근거가 됩니다.**

#### 철회 ① — "검색 신호를 걸러내면 경보 품질이 2배 좋아진다" (09.22 철회)

- **처음 보고한 내용**: 공휴일·축제로 설명되는 신호를 빼면 상승도가 1.17 → 1.99배로 오른다
- **무엇이 틀렸나**: 적중률을 **전국 평균**과 비교했습니다. 그런데 필터를 통과한 신호는 원래 급증이 잦은 지역에 몰려 있었습니다. 그 지역들의 고유 급증률로 다시 계산하니 **1.03배**로 개선이 사라졌습니다
- **어떻게 잡았나**: ① 기저율을 지역별로 다시 계산 ② 경보 기준을 0.5%/1%/2%로 바꿔보니 결론이 제각각(0.00 / 1.03 / 1.15)
- **교훈**: 비율 지표는 **비교 대상을 명시**하고 **기준을 바꿔도 유지되는지** 확인해야 합니다

#### 철회 ② — "전년 대비 방문 급증 43건을 탐지했다" (09.24 철회)

- **처음 보고한 내용**: 시군구 급증 43건 중 41건이 공휴일이다
- **무엇이 틀렸나**: 43건 중 **42건이 2026년 2월**이었습니다. 우리 기준이 364일 전과 비교하는데, **2025년 설은 1월 28~30일, 2026년 설은 2월 16~18일**입니다. 연휴가 있는 날과 없는 날을 비교한 셈입니다
- **어떻게 잡았나**: 명절을 **날짜가 아니라 명절끼리** 맞춰 다시 쟀습니다. 전국 228지역 배율 중앙값 1.12배, 최대 1.66배, **급증 기준(1.82배)을 넘는 지역 0곳**
- **의미**: 2026년 상반기 시군구 총량에는 '급증'이라 부를 사건이 사실상 없습니다. 이건 **우리 주장을 강화합니다** — "총량으로는 안 보이니 지점을 봐야 한다"의 근거가 됩니다

**팀에 부탁**: 이 두 문장은 **어디에도 쓰지 마세요.** 쓰면 안 되는 문장 목록은 [`확정수치_0924.md`](확정수치_0924.md) 하단에 있습니다.

## 7. 직접 돌려보는 법

### 7-1. 가장 자주 쓸 명령 — 숫자가 그대로인지 확인

```bash
uv run python analysis/src/forecast/freeze.py --check
```

10초면 끝납니다. 이렇게 나오면 정상입니다.

```
동결 시각 2026-09-24 09:45 · 수치 43개 대조
입력 데이터 지문 일치

모든 수치가 동결본과 같습니다. 서식4의 숫자를 그대로 쓰면 됩니다.
```

숫자가 달라졌으면 이렇게 알려줍니다.

```
달라진 수치 2개 — 서식4를 고쳐야 합니다
  데이터랩포함_sMAPE   동결 8.979 → 현재 8.812   (ablation_h7.json)
```

**서식4를 쓰기 전과 제출 직전에 한 번씩 돌려 주세요.**

### 7-2. 전체 재실행

```bash
uv run python analysis/src/forecast/run_all.py
```

13단계를 순서대로 돌리고 마지막에 자동으로 대조까지 합니다. **약 10분** 걸립니다. DB 접속이 필요합니다.

DB 없이 돌리려면(패널 파일이 이미 있을 때):

```bash
uv run python analysis/src/forecast/run_all.py --offline
```

### 7-3. 제출 첨부 Zip 만들기

```bash
uv run python scripts/build_submission_zip.py
```

그림·검증보고서·사례·수치·코드·운영규칙을 폴더로 묶어 `docs/submission/제출첨부_YYYYMMDD.zip`을 만듭니다(현재 0.8MB). `.env` 같은 민감 파일은 자동으로 빠집니다.

### 7-4. 잘 안 될 때

| 증상 | 원인과 해결 |
| --- | --- |
| `python`을 쳤는데 멈춰 있다 | 윈도우 기본 python이 아니라 **`uv run python`**을 쓰세요 |
| DB 접속 실패 | `.env` 파일이 있는지, 팀 채팅의 접속 정보가 맞는지 확인 |
| 한글이 깨져 보인다 | 터미널 인코딩 문제입니다. 결과 파일(json/md)을 직접 열어보세요 |
| `panel_daily.csv가 없다` | [`build_panel.py`](../analysis/src/forecast/build_panel.py)를 먼저 돌려야 합니다 |
| 실행이 너무 오래 걸린다 | [`ablation.py`](../analysis/src/forecast/ablation.py)는 원래 3분씩 걸립니다. `--quick` 옵션으로 건너뛸 수 있습니다 |

## 9. 자주 나올 질문과 답

### 9-1. 팀 내부에서 나올 질문

**Q. 검색이 안 된다는 게 확정인가요? 우리 프로젝트 전제였는데요.**
A. 확정입니다. 세 가지 방식으로 각각 확인했고 전부 같은 결론입니다. ① 예측에 넣어봤을 때 기여 없음(+0.026%p) ② 급증을 예고하는지 봤을 때 상승도 1.0~1.25(기준 바꾸면 뒤집힘) ③ 지점 급증을 가려내는지 봤을 때 AUC 0.482. **다만 이건 "시군구 단위에서"입니다.** 영월 사례처럼 개별 사건의 타임라인에서는 검색이 먼저 움직인 게 보입니다. 그래서 사례 서술에는 계속 씁니다.

**Q. 그럼 우리 프로젝트가 실패한 건가요?**
A. 아닙니다. 전제 하나가 틀렸을 뿐이고, 그걸 **데이터로 증명한 것 자체가 결과**입니다. 그리고 대신 더 단단한 발견(지점 쏠림 98% 사각지대)을 얻었습니다. 이 대회는 "데이터랩을 어떻게 활용했는가"를 보는데, 우리는 **데이터랩 지표의 실효성을 정량 평가한 유일한 팀**이 될 수 있습니다.

**Q. 숫자가 자꾸 바뀌는 것 같은데 뭘 믿어야 하나요?**
A. [`확정수치_0924.md`](확정수치_0924.md) **하나만** 믿으세요. 43개 숫자가 출처와 함께 고정돼 있고, 대화 기록이나 스크립트 출력에서 옮기면 안 됩니다. 제출 직전에 `freeze.py --check`로 대조합니다.

**Q. 제가 뭘 하면 되나요?**
A. 팀 확정 4건(제목·성과분야·서비스명·발표 대표자)과 웹 화면 캡처입니다. 캡처는 [`docs/submission/web_screenshots/`](submission/)에 넣으면 제출 Zip에 자동으로 들어갑니다.

### 9-2. 심사·발표에서 나올 질문

**Q. 관광지 하나가 뛰어도 시군구 총량이 안 움직이는 건 당연하지 않나요?**
A. 맞습니다. 저희는 그 '당연함'의 크기를 쟀습니다. 지점 급증이 총량에 남기는 흔적은 중앙값 0.38%p인데, 총량은 평소에도 ±6.1%p 흔들립니다. 신호가 잡음의 1/16입니다. 총량을 1.2배로 올리려면 그 지점 혼자 54배가 되어야 합니다. **즉 놓친 게 아니라 감지할 수 없는 것이고, 그래서 감시 단위를 바꿔야 한다는 결론이 나옵니다.**

**Q. 2026년만 그런 것 아닌가요?**
A. 2025년 같은 기간에 같은 절차를 그대로 돌렸고 96%로 동일했습니다(95% 구간 92~100%).

**Q. 보고하는 지점이 달마다 달라지는데 표본 문제 아닌가요?**
A. 4개월을 모두 보고한 482개 지점만으로 다시 계산하면 84건 중 84건, 100%입니다.

**Q. 백테스트 성능이 실제 운영에서도 나오나요?**
A. 그러도록 설계했습니다. 이동통신 방문자는 4일 지연, 데이터랩은 매월 17일 전월분 공개라는 실제 공개 일정을 코드에 규칙으로 넣었고, 날씨는 예보가 아니라 관측이므로 운영 모델에서 뺐습니다. 변수별 판단은 [`분석_누출점검표.md`](분석_누출점검표.md)에 표로 있습니다.

**Q. 재현 가능한가요?**
A. 명령 하나로 DB 조회부터 그림까지 13단계가 10분에 재실행되고, 문서의 수치 43개가 자동 대조됩니다. 하나라도 다르면 어떤 값이 어떻게 달라졌는지 알려주고 실패로 끝납니다.

**Q. 급증의 원인은 확인했나요?**
A. 절대 증가폭 상위 5곳을 추적해 3곳에서 특정했습니다 — 축제(김제 모악산 뮤직페스티벌 +11.4만 명), 대형 전시(경남도립미술관 이건희컬렉션 순회전), 지자체 생태관광 육성사업(창원 주남저수지 +8.0만 명). **세 건 모두 같은 달 시군구 총량은 0.99~1.03배였습니다.** 나머지 2곳은 확인하지 못했고, 그대로 적어 두었습니다.

## 부록 A. 용어집

분석 문서에 나오는 말을 쉬운 순서로 풀었습니다.

| 용어 | 뜻 | 우리 경우 |
| --- | --- | --- |
| **패널** | 지역과 날짜를 행으로 쌓은 큰 표 | 228지역 × 1,322일 = 301,416행 |
| **백테스트** | 과거 데이터로 "그때 이 방법을 썼다면 어땠을까"를 재보는 것 | 2026년을 시험 구간으로 사용 |
| **sMAPE** | 예측이 평균 몇 % 틀리는지 재는 지표. 낮을수록 좋음 | 8.98% = 1만 명 예측에 약 900명 오차 |
| **MAE** | 평균 몇 명 틀렸는지(사람 수 단위) | 7,871명 |
| **누출(leakage)** | 예측 시점에 알 수 없는 정보를 몰래 쓰는 것 | 4일 지연·17일 공개 규칙으로 차단 |
| **공개 지연** | 데이터가 실제로 손에 들어오기까지 걸리는 시간 | 이동통신 4일, 데이터랩 익월 17일 |
| **시간 순 분할** | 과거로 배우고 미래를 맞히도록 나누는 것 | 학습 23~24 / 조정 25 / 시험 26 |
| **잔차** | 실제값 − 모델이 예상한 값 | 이게 크면 "설명되지 않는 급증" |
| **씨앗(seed)** | 모델 학습의 난수 초깃값 | 바꿔 돌려보며 흔들림 폭을 측정 |
| **위약(placebo) 검사** | 일부러 가짜 데이터를 넣어 결과가 무너지는지 보는 것 | 정답 섞기, 지역 이름표 섞기 |
| **위약 대조군** | 진짜 데이터 효과에서 빼야 할 '가짜도 내는 효과' | 0.113%p |
| **신뢰구간** | 그 수치가 있을 만한 범위 | 0을 포함하면 "차이 없음" |
| **붓스트랩** | 표본을 다시 뽑아가며 구간을 추정하는 방법 | 지역·시군구 단위로 2,000회 |
| **지역 승률** | 228개 지역 중 좋아진 지역의 비율 | 데이터랩 75.4% |
| **기저율** | 아무렇게나 골라도 맞을 확률 | 이것과 비교해야 신호가 의미 있음 |
| **상승도(lift)** | 적중률 ÷ 기저율. 1.0이면 무의미 | 검색 신호 1.03~1.25 |
| **AUC** | 순위를 매겨 가려내는 능력. 0.5=동전, 1.0=완벽, 0.5 미만=반대 | 조기경보 0.217 |
| **임계(threshold)** | 이 값을 넘으면 급증/경보로 본다는 기준선 | 지점 2배, 시군구 1.82배 |
| **임계 민감도** | 기준을 바꿔도 결론이 유지되는지 | 유지되지 않으면 그 결론은 버림 |
| **명절 정렬** | 날짜가 아니라 명절끼리 맞춰 비교하는 것 | 설 이동 오염 제거 |
| **균형 패널** | 모든 기간을 빠짐없이 보고한 대상만 남긴 표 | 482개 지점 |
| **GBM(부스팅)** | 작은 결정 규칙을 여러 개 쌓아 예측하는 모델 | 우리 채택 모델 |
| **Ridge** | 단순한 선형 모델 | 비교용, 10.05% |
| **ETS·SARIMAX** | 전통적인 시계열 모델 | 비교용, 21~29%로 뒤짐 |

## 마지막으로 — 이 작업의 성격

분석 결과 중 **"성공"보다 "실패"가 더 많습니다.** 검색은 기여하지 않았고, 조기경보는 안 됐고, 주장 두 개를 철회했습니다.

그런데 그 실패들이 하나씩 쌓이면서 **"시군구 총량으로는 원리적으로 볼 수 없다"**는 결론이 나왔고, 그게 지금 우리 서식4의 가장 강한 문장입니다. 그리고 실패를 감추지 않고 검증 과정을 그대로 보여주는 것이, 운영 실적이 없는 우리가 내놓을 수 있는 가장 좋은 카드라고 생각합니다.

궁금한 점이나 이상해 보이는 숫자가 있으면 언제든 알려주세요. 전부 재현 가능하게 만들어 뒀습니다.
